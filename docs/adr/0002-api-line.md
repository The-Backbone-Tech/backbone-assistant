# ADR 0002: The api line: what another process may ask of a running app

**Status:** accepted for review, 1 Nov 2026. Amended 2 Nov 2026: three reads joined for the MCP door's read tools, and `backbone-mcp host` serves the line with reads and Stop only, as "Revisit when" foresaw. Amended 4 Nov 2026: four writes joined, each behind the same per-call click as a send (`queue.add`, `goals.set`, `goals.run`, `schedules.create`); a host with no one at it still carries none. Amended 5 Nov 2026: on a chat whose task was chosen a route (solution selection), a send, a queued message and a goal run show that route, its limits and the model it runs, and are pinned to it. Amended 10 Nov 2026: audit metadata reads with keyed commitments, connection-owned bounded sessions and startup-only stale-copy cleanup; content remains direct-only. Amended 11 Nov 2026: solution options and exact-version verification are reads; choosing and running a task is an asked write. Amended 14 Nov 2026: the local app and daemon may explicitly enable project creation and local file attachment without starting model work. Each amendment waits for another-family review.

**Context.** A real data folder's keys are in the Keychain, which only the app's main process reads, so the command line could not reach a real data folder. Giving it the keys is out. The other way is a socket into the running app. Unix permissions stop at the user: any process of the person's user can open it, including an AI tool on a narrow door permission and anything an agent starts. Carrying the whole `api` would hand all of them `terminal.run`, `settings.model.put` and the person's model key to spend.

**Decision.**

- **The line:** `<home>/run/api.sock` beside the door's socket, in the same folder only the person's user may enter (mode 0700, checked to be a real folder of theirs on both sides), itself 0600; the door's `/tmp` fallback for a long data folder path. The app serves it once its core is up and removes it on quit. The door's socket and its four calls do not change. The line is `packages/platform/src/doors/api-line.ts` and `packages/platform/src/composition/api-line.ts`.
- **Default deny.** It carries exactly `API_LINE_METHODS`: the reads, `turns.stop`, and the asked writes, `API_LINE_ASKED`. `API_LINE_PROJECTS` adds exactly `projects.create` only when the local app or daemon enables `projectCreation`; it stays closed on other lines. `API_LINE_ATTACHMENTS` adds exactly `material.attach` only when the local app or daemon enables `attachment`; it stays closed on other lines. `API_LINE_TEAM` separately carries the shared daemon’s local team controls. Anything else is refused before the host hears of it. Each call's arguments are checked and rebuilt from its named fields. `connectTool` and `signCapability` are not api methods and stay off every transport.
- **Who may do what:**

| Call | Who | Why |
| --- | --- | --- |
| `projects.create` | Any process of the device owner's operating-system user that can open the socket folder, including agents with door access and their child processes, when explicitly enabled by the personal app or daemon | Creates an empty project owned by the device owner under that data folder and records it for listing and sharing, subject to the Host’s current identity checks; Git projects include only the setup README and initial commit. This request does nothing else: it starts no model work, changes no permission, accepts no destination path and gives no access to existing projects. On a verified workspace it also registers that project in Core as the device person. This bounded local registration authority is deliberately available without a click to those same-user processes; possession of a narrow door permission does not narrow operating-system socket access. Company sign-in configurations refuse this request and direct the caller to create the project in the signed-in app. The line checks a nonempty plain name of at most 1,000 characters, kind `folder` or `git` and a nonempty plain client key of at most 256 characters, then rebuilds only those fields. The CLI supplies a fresh key for the existing durable project-creation intent. A refusal stays refused; an interrupted intent or lost answer stays unknown and is never retried automatically. No app click is needed. Each serving app or daemon composition must supply its creation budget or the line refuses to serve: at most 10 validated requests in a rolling minute and 100 until that owner restarts, shared across all its connections and replacement lines, counting failed and repeated requests too; excess requests are refused immediately in plain words and never queued. Each Git invocation is killed after twenty seconds, including a child ignoring normal termination. Durable intent files have no existing cleanup and are retained to prevent replay after interruption; they can accumulate across restarts. This amendment adds no cleaner. This opt-in supplies no network capability: the shared HTTP listener still uses authenticated workspace permissions, never the device-owner call. |
| `material.attach` | Any process of the device owner's operating-system user that can open the socket folder, including agents with door access and their child processes; possession of a narrow door permission does not narrow operating-system socket access. Attachment is explicitly enabled by the personal app or daemon | The CLI reads its local regular file and sends bytes, never a source or destination path. The line rebuilds only project id, basename, base64 bytes and media type; caller-supplied relative paths and extra fields cannot select a write target. Names reuse exactly the direct attachment basename and intermediate-file rules, including names with Unicode format characters. Only project id and media type are limited to 1,000 plain characters; the frame bounds filename metadata. Canonical base64 must decode to at most 25 MiB, including empty files; malformed or oversized requests are refused before Host dispatch. Before accepting a greeting, every connection has a 1 MiB byte ceiling. After greeting, only an attachment frame whose first 128 characters announce the existing client header (id, then method `material.attach`, then args) may exceed it, and only when attachment is enabled as `true`, never under company sign-in. At most one connection per line server may hold a partial frame above 1 MiB; another is closed, and completion or disconnect releases the slot. The large frame is bounded in UTF-8 bytes to the encoded 25 MiB plus 64 KiB metadata; all other frames retain the 1 MiB ceiling before parsing. The same Host operation used directly and by the app checks project access, retains original bytes and allocates names/versions under its lock, with storage write admission immediately before attachment. Entries are recorded as the person's originals (`class: original`, `by: person`), visible to colleagues who have access to the project. Here person means the device owner's operating-system user, not a verified human action. A typed write-admission refusal before attachment begins says nothing was attached; a failure after attachment begins or a lost answer remains not known. No model work or permission change starts. Company sign-in directs attachment to the signed-in app. Enabling attachment without an owner-supplied budget refuses startup before writing: 10 validated attempts per rolling minute and 100 until the owner restarts, shared across connections and replacement lines, including failed and repeated requests. As with project creation, a validated attempt refused by Host write admission still counts; the line cannot reset the owner's allowance. Excess is refused immediately, never queued. At the file limit this bounds new original bytes to 250 MiB per minute and 2.5 GiB per process lifetime; projections add storage overhead. The separate budget follows project creation's policy to bound local disk ingestion. Attach has no durable client key: a repeated successful call creates another original under a free name, as direct attach does. A lost answer is not known and is never retried automatically; inspect the project before another attachment. This is local same-user authority, unavailable through the shared HTTP listener or other hosts by default. |
| `projects.list`, `threads.list`, `threads.get`, `work.now`, `files.list`, `material.read`, `changes.get`, `models.list`, `settings.model.get`, `settings.policy.get` | Any process of the person's user | Same-user processes can already read these in the data folder's plain files. They start nothing. `material.read` and `changes.get` (added 5 November, for the terminal chat's file and diff pane) read a document's stored versions, which are plain files under the data folder's `material/` folder, and compute a diff between two of them. A document id must be one plain path segment, checked at the line and in the store, so no id reaches another data folder. They write nothing of their own; opening a document whose save a kill interrupted records that interruption, as any open of it in the app does. |
| `threads.search`, `goals.runs`, `schedules.get`, `memory.search` | Any process of the person's user | Each answers from the host's memory of what the data folder's plain files hold: the threads `threads.get` already carries, `goal-runs.json`, `proactivity.json`, the memory files. None writes a file or starts a turn; `schedules.get` at most rolls the in-memory day counter the ticker rolls anyway. `memory.search` was off while reading tidied the memory files; it now reads without writing, and leaves out lines of withdrawn sources. |
| `solutions.options`, `solutions.verify` | Any process of the person's user | Options probe loopback model catalogues and the existing client status, with no inference. An explicit public evidence topic optionally reads Arena through its local query. Verification reads the exact material version and receipt of the named turn, reports later edits separately and establishes custody and format, not factual correctness. |
| `solutions.run` | One task, after the person's click | The selector computes a choice before the question. The question shows its route, model the initial turn will dispatch (a differing named native model is refused before asking), spend class, ordinary billing warning, complete task, project/thread, settings and hard limits. The call binds the choice through an opaque endpoint/credential-handle fingerprint and model constraint; changes during confirmation or before dispatch are refused. The Host records dispatch. Codex billing status is freshly checked for options and admission rather than cached across sign-in changes. MCP requests are capped at ask permission; the question distinguishes a claimed client name (at most 60 characters) from a missing name. This cap applies to the MCP tool only; a same-user client with shell access can also invoke the CLI or API line directly. Empty attachment lists only. A headless host has no confirmation and cannot run it. A lost call is unknown outcome and never retried automatically. |
| `audit.export` without content | Any process of the person's user, including an agent shell child or a tool on a narrow door permission | Explicit owner decision, 10 November 2026: this is a read of the database ledger, not a projection already in plain files. The process learns ids, times, operation classes and outcomes across the whole data folder, plus allowlisted structural metadata and Core receipt anchors; no work content or raw private-content commitments. The published piece-file digest remains plain on piece registration facts. Receipt anchors and private payload digests are domain-separated HMACs under an audit-only key derived with HKDF-SHA-256 from the credential master; the header carries a short keyed identifier, never key material. The service role cannot call sec.digest and no Core permission is widened. Either transport uses the explicitly labelled service-secret fallback when the data folder has no credential master; only writable owning Host startup prepares that master, never a diagnostic or read-only open. A file holder can see repeated descriptions, separate permissions sharing a constant per-call note from permissions with their own note, and count them. These are inferences, not a structured statement of which permission allowed a call, and may change with the Core unit that records which permission allowed a call. Keyed commitments provide no offline guessing oracle for omitted private values without the secret. A raw-hash content export, available only directly, exposes a ledger-hash guessing oracle even for other omitted strings. SQL still requires the data folder's active owner/admin person and preserves row visibility for receipt enrichment. It starts no work and gives no permission. The header identifies only a same-user process, not the person. Content is refused for every caller on this line; adding it requires an asked call confirmed by the person in the app, which is not built. Paging/cancellation only manage this read and reveal no additional fields. |
| `core.signatureStatus` | Any process of the person's user | Pure inspection through the held data folder's existing Core read connection, using the same installation-history and exact-profile verifier as the connector service. Returns only the fixed step name `connector-signature-ledger-v1` and verified/paused state. It opens no vault, installs nothing, changes no file or ledger row and starts no work. It lets doctor explain why permissions are unavailable without exposing database text or credentials. |
| `turns.stop` | Any process of the person's user | It only ends work. That user can already kill the app. |
| `turns.send` | One send, after the person clicks Allow for it in the app's own dialog, in the main process | It can spend their model route. Nothing else can make this click. On a chat whose task was chosen a route, the send continues that route: the dialog shows it, the task's limits and the model that route runs (the one the turn goes to), and the send carries what was shown (`continues`), so the host refuses it if the chat's route moved. A model the settings name that the chosen route cannot run is refused before anything is asked; a native engine runs the named model on its chosen engine and account. |
| `queue.add` | One message, after the person's click for it, as a send | It becomes a turn when the turn in hand ends, or at once on an idle chat, so it spends their route as a send does. The dialog shows the thread, the effective settings (a child's pinned model, not the one asked for) and all its words. Like a send, it carries no attachment and runs on this computer, and on a selected chat it shows and is pinned to the chosen route; the queued message keeps that pin until it is sent, and waits with the reason if the route moved. |
| `goals.set` | One goal, after the person's click for it | It starts no work, but it is what a goal run works toward and what its check judges the work against, and a schedule on the chat works toward it too. A process that could change it unseen could steer the person's later, approved runs. The dialog shows the thread and all the goal's words. Clearing a goal stays in the app. |
| `goals.run` | One run, after the person's click for it | It starts up to `budget` turns of work (1 to 50) on their route with no further question, each followed by a check turn: up to twice `budget` model turns, which the dialog says. It shows the thread, the chat's goal as the host holds it, all its words, and the settings the run takes from the chat's latest turn. The run is pinned to those settings and that goal (`GoalRun.settings`, `GoalRun.goal`): later turns do not change how it runs, and a changed goal pauses it. On a chat whose task was chosen a route, the dialog shows that route and the run records it (`GoalRun.selection`) for its work and its checks; a later, unrelated choice in the chat does not move it, and a recorded route that moved refuses the run's next turn rather than run elsewhere. A run started without settings pins the chat's latest when it starts. |
| `schedules.create` | One schedule, after the person's click for it | Each run is a turn on their route, with no further question, until they pause or delete it in the app: the most spending behind one click. The dialog shows the project and thread, the person's words for when, how the host read them with the time of day each run takes, the first run, the effective settings, and all the words each run sends (trimmed, as they run), or the chat's goal when it works toward that. The schedule is made from the rule and anchor the person was shown, never from `when` read again, and is refused if its first run is no longer the one shown. A goal schedule is pinned to the goal it showed: if that goal changes, the schedule pauses and says why until the person resumes it, which takes the goal as it is then. Words the host cannot read as a time are refused before anything is asked. Its runs go on the route it was allowed on and never adopt a route chosen in the chat, before or after; a run whose route would carry a selected task's work outside that task's limits is skipped with the reason. |

- **The click is for the whole write, and exactly what was shown runs.** The line resolves each write from the host's own state before asking: trimmed words, a goal as the host holds it, names, the effective settings and, for a schedule, its parsed times. After the click it resolves it again and runs only if nothing it showed has moved, such as the goal, a child's model, the chat's latest settings, a name, or another question approved ahead of it. Then it runs the resolved snapshot, not values derived again. Every text the dialog shows, a goal or a name the host holds included, meets the checks below, or nothing is asked. What follows says it for a send. The dialog shows every field: project and thread with their ids, model, effort, permission, mode and all its words. Nothing is clipped, because the line refuses text over `MAX_ASKED` (1,000 characters) and text with control or format characters or Unicode's line separators, which could show the person something other than what is sent. The words may hold newlines and tabs, which the dialog shows quoted and escaped. The model and every id must be one plain line, so no field can pass for another: those characters, newline and tab included, are refused before the dialog is built. A longer send goes through the app.
- **No click stands.** Allow covers the one turn, message, goal, run or schedule the dialog shows, so a process with a narrow door permission cannot ride on the person's approval of something else. The cost is deliberate: an unattended script cannot send. A standing permission was built first and rejected in review. Don't allow closes every asked write until the app reopens, held in the app's memory, so a process cannot wear the person down by asking again. One question shows at a time. A question nobody answers within two minutes is taken down, refuses that send and is not a No. A caller gone by the time of the click starts nothing. A host that passes no `confirm` carries no asked write: `backbone-mcp host`, a test data folder's headless host, serves the line that way, so its line carries reads and Stop only. The daemon (`backbone daemon run`) refuses model-work writes and Stop. Its explicit local project-creation, attachment and shared team controls are separate from asked writes.
- **A send carries no attachment and runs on this computer.** Use `files attach` separately for an original; attachment during a send remains unavailable through this line.
- **No secret crosses.** Secrets in keys and credentials never cross: the Keychain, the vault and keys are never on the line, and the client never opens them. `settings.model.get` loses `own.baseUrl`, which can hold a token. A thrown error crosses only as "failed": its words can name a connection.
- **Outcomes.** A line lost mid-call is unknown and is never resent; the client has no retry. A running turn is not settled, so `threads show` exits 4 for it. A read attaches to the live host and so never recovers or starts anything.
- **With the app closed** the command line reads the vault's `holder` word and opens a data folder only if it says `plaintext`, or if the data folder is new. The Keychain gets that plain reason; an unreadable vault or another word is refused too, and so is a data folder that holds `data`, `projects.json`, `cluster.json` or a thread with no vault. It starts no host.

**Stated limits, accepted.**

- **One click can authorise later spending.** A goal run's budget (twice that in model turns, with its checks) and a schedule's runs go on after the click, with no further question; the dialog says so and shows the budget or the times. The person ends them in the app (pause, delete) or with `turns.stop`.
- **A schedule's settings are its own.** They are pinned when it is made; a child's model is shown and pinned as the child's.

- **`turns.stop` stays open to the person's own user.** It only narrows, ending work and starting none, and that user can already kill the app. A process on a narrow door permission can therefore stop work it did not start.
- **Stop has no key.** It is repeatable, and nothing resends it.
- **Thread text crosses on reads.** The same user can read it in the data folder's plain files, so this line adds no reach. If a person pasted a key into a conversation, that text crosses like any other. Secrets in keys and credentials still never cross.

**What this does not stop.** The click is the boundary, and it is one person reading one dialog. The dialog's words come from the caller, so they are quoted and labelled, and the person cannot learn which program asked: Node exposes no peer credentials here. A same-user process that can drive the screen (Accessibility) can click for them. Same-user reads of the data folder's plain files were already possible and still are.

**Owner decision pending: unattended writes.** Scorecard row 8 (Proactivity) counts the daemon's read-only line against the bar: work is started from the app. Letting the daemon, or any host with no one at it, start model work without a click is the standing permission this record rejected above. It would take the maintainer amending this record, with its own another-family review. Local project creation and attachment start no model work and do not decide it, and nothing here makes it easier to slip in: a headless host refuses every asked write, tested.
