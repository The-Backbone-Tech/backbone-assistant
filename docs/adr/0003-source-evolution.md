# ADR 0003: immutable Core bootstrap and explicit schema versions

Status: accepted, 10 November 2026. Adopted by the integrator; implemented with the first real material closure version.

Context: released material steps select exact statements from the shipped bootstrap. Editing those statements breaks the published assemblers. The earlier manifest expanded wildcards, so adding a file could silently alter a fresh installation. Baseline history digests remain shape-checked, independently of build-artifact integrity.

Decision:

- The bootstrap freezes the qualified post-A1c source at 78c12d0b: 251 ordered files, per-file raw SHA-256, assembled body checksum bfd246fcc4bd352ea9bb61114e827a20cae79c8b6bcc6359cef91965b0d8d21c and full artifact checksum in schema/baseline.json. A1c is the last bootstrap-mutating lane for this transition. Every new Core schema object belongs to an explicit version; other in-flight bootstrap additions are re-planned. There are no discovery wildcards. This applies to every Core lane.
- Retain the current bootstrap files at their existing paths. New schema versions are linear and append-only. Each version has one closed bundle. A bundle becomes immutable when its checksum enters CORE_SCHEMA_UPGRADES. Later versions may replace an object again.
- Define an object once per version. The active definition is its definition in the latest version listing it, otherwise the bootstrap definition. A checked/generated current-definition index points to the active file without requiring chat history.
- Each bundle manifest lists exact prerequisite versions/checksums, added and replaced signature-exact objects, ordered source files, their hashes and the payload checksum. That checksum must match CORE_SCHEMA_UPGRADES. Unlisted SQL, duplicate definitions in a version, adding an existing object, replacing an absent object and changed released sources fail checks. Function-text patching stays forbidden. Normal per-file line limits remain; there is no directory-wide exclusion.
- A bundle is a separate closed build artifact. Never concatenate it into baselineSql or reuse bootstrap block markers inside that string. Runtime uses the packaged exact payload, not developer schema paths or arbitrary caller-selected DDL.
- Fresh installations run the frozen bootstrap, recognized historical installers and the next real step. Known upgrades reach the identical final profile. Unknown/mixed/external data folders receive no guessed migration or invented receipt. Distinguish the frozen build artifact from historical database baseline receipts: never rewrite an old receipt to the new checksum. Keep the existing reviewed historical-admission policy: the baseline receipt must be exactly 64 lowercase hexadecimal characters, the upgrade sequence must contain only the declared ordered version/checksum pairs, and the complete prerequisite catalogue/profile must verify before applying the new step. All three conditions are required; a checksum alone authorizes nothing. This preserves the real legacy fixture and supported data folders instead of inventing a retroactive finite baseline-checksum list. Any later tightening to a finite historical checksum/profile set is a separate reviewed change. Controls must show that the legacy fixture upgrades with its original receipt and that an arbitrary checksum-shaped receipt over an incomplete or tampered catalogue pauses.
- Choose the verifier by exact history. Old histories use the old exact verifiers. New history uses one acyclic complete-superset profile covering every previously attested guard/link/enforcement object, role, ACL, RLS policy, trigger, dependency and the exact 59-signature prior union (guard 23, link 17, enforcement 21 = two introduced plus 19 prior carrier/park/wake functions). Only explicitly replaced objects move to new pins; unchanged coverage is retained. CoreLink derives all three material statuses for new history from that complete verifier. Each later independently attested capability retains its own authority. In particular, A1c's signature-ledger.ts prerequisite selects the new material status on new history and the old prerequisite on old history; its own catalogue pins/checksum stay intact, without a verifier cycle. A verified profile never activates material. A changed-object-only verifier is forbidden.
- Install replacements under their owning roles. CREATE OR REPLACE preserves OID, owner and ACL but cannot change a function signature, return type or OUT parameters; replacing a view can append columns only. Restate and verify SECURITY DEFINER, search_path and ACLs. A signature change needs an explicit new crossing/compatibility design, not DROP/CREATE through dependent policies or triggers.
- Specifically, traceable recall cannot add OUT fields to the old two-column recall permission through CREATE OR REPLACE. Design a new typed crossing or another reviewed compatibility path. Old clients must remain safely message/web-only or explicitly refused for material; changing the shared eligibility view must not accidentally let an old untraced recall return material words.
- Every bundle declares how in-flight callers are serialized. For candidate creation: bounded lock_timeout/statement_timeout, existing schema lock, candidate-table SHARE ROW EXCLUSIVE before replacement/trigger, then a per-workspace head-locked ledger boundary; values recomputed after the lock by an ALWAYS BEFORE INSERT trigger. Old/direct inserts and new-workspace initialization are covered; the actual implementation must handle a head-first caller meeting the table-first installer by a bounded clean abort/rollback and retry, never partial receipt or an indefinite wait. The implementation uses NOWAIT ordered head acquisition after table serialization, releasing all locks before retry; no claim of universal inversion-free progress is made. Replaced authority crossings obey the revised authority contract's READ COMMITTED refusal and separate post-wait statements.
- DDL, exact catalogue verification, boundary records and the receipt commit in one transaction under the existing schema lock. Qualification must include fresh/known-upgrade equality, supported old callers, warmed plans, compile-checking every new function, rollback/kill cases, admission and exact-profile tamper negatives. A source-check pass does not claim those native controls passed. No pin is learned from a live data folder catalogue.

There is no down-migration. A faulty released bundle is corrected by a later version. Rollback/death controls concern the uncommitted installer transaction, not reversal of published history.

Enforced by: the SQL-definition rule (sqlProblems), closed manifest/source checker (packages/core/scripts/closed-version.mjs), exact bundle checksum equality with CORE_SCHEMA_UPGRADES, reproduction controls for all three released material steps and A1c's actual integrated step, and the generated current-definition index check. The source checker enforces byte provenance and declared function, relation, index and trigger identities; it does not classify every ALTER, GRANT, REVOKE, CREATE POLICY, COMMENT or DROP statement as an object change. Full columns, policies, trigger flags, ACLs, constraints, roles and dependency closure require exact native catalogue qualification and independent diff review. Regenerating hashes or pins alone does not approve a change in those properties. Per-rule controls must reject the named fault with a matched diagnostic; a whole-manifest digest alone does not establish each field check.

Consequences: the current one-definition-per-package/no-patch-chain wording becomes one canonical definition per explicit version, with a discoverable active-definition index. Historical executable bootstrap and upgrade assets stay distinguishable from active target source. This is a deliberate repository/architecture contract change. It does not enable material-backed decisions, recall or final use.

Revisit when: a real bundle exposes a concrete unsupported dependency, permission or installation boundary. This does not create a general migration service, schedule or catalogue refresh.
