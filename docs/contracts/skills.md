# skills contract (DRAFT 0)

**Owner:** integrator (core).

**Layer:** L0.

**Status:** have.

## Purpose

Reusable procedures in the Agent Skills format, versioned by hash, quarantined until evaluated. **A skill never permits authority.**

## Owns

- skill versions (SHA-256);
- quarantine state;
- evaluations;
- retirements.

## Provides

- `gov.load_skill`;
- `gov.record_skill_evaluation`;
- use and retire.

## Consumes

- knowledge-memory (promotion of a skill);
- mandates-decisions.

## Rules

- Skill words are read content, so taint applies (M0018 `review_skill_words`).
- A third-party skill enters quarantine.
- A skill cannot raise an effect class or widen a mandate.

## Built: skills shared across engines

Built in `packages/platform` (`src/memory/imports.ts`, `src/composition/memory.ts`). SKILL.md folders are found in the data folder's `skills/` and `.claude/skills`, `.codex/skills` and `.agents/skills` in the person's home folder, the `skills/` folders of the Claude Code plugins they enabled (`enabledPlugins` true in `$HOME/.claude/settings.json`, at the install folder `$HOME/.claude/plugins/installed_plugins.json` records, read only when it lies inside `$HOME/.claude/plugins/cache`; of `settings.json` only `enabledPlugins` is used), and the skills of the Codex plugins they enabled (the installs the next section names: the root `skills/` folder, where Codex documents that portable packages keep them, and the `skills` folder `.codex-plugin/plugin.json` declares when the root `plugin.json` has no `extensions["com.openai"]` object, read only when it starts with `./` and resolves inside the plugin's own folder through no link). A plugin's MCP servers are read by connectors, and its commands, agents and hooks as the next section says, read only when the host is given that folder (`memory.userHome`): the app gives it for the person's default profile, and any other data folder (one named by `BACKBONE_HOME`, the command line, the daemon) only when `BACKBONE_USER_HOME` names it. Without it no personal folder is listed, and importing from Codex or Claude is refused. One found in the person's folders is listed as available and given to no turn until they enable it; enabling pins its text, so a skill changed afterwards waits again, and one holding a credential cannot be enabled. A plugin's skill (`Skill.plugin` names its plugin) follows the plugin rules of the next section: once its text is seen to differ from its pin, or it is no longer read (a link, moved, its plugin turned off), the permission is removed from `skills/.enabled.json` for good, so the old text coming back leaves it off; if that removal cannot be written, every plugin skill is off for the life of the process and says why (`Skill.blocked`). A credential in any of its fields, its text or its plugin's manifests (raw and decoded, split across separators too) blocks it: every field of its own is withheld, it cannot be enabled, and it is never offered; with the stored credentials unreadable, every plugin skill's fields are withheld. A turn is given the text of at most two enabled skills whose name or description share its words, through `TurnRequest.memory`, as reference beside the person's words, never as system instructions; a skill changes no permission. Reads follow the same rules as imports (no links, single-link files, inside the named root). A skill drafted from a chat's finished turn (`skills.draft`) is refused if its words hold a credential, records the documents that turn was given as its sources (in its front matter and in `skills/.sources.json`), and waits under `skills/.proposed` until the person accepts it (`skills.decide`), which is the only quarantine built. When any of its sources is withdrawn, the drafted skill, proposed or accepted, leaves the disk on the same purge as memory, and delivery skips it even before the purge runs. Accepted limit: a skill's text remains model input that can steer, labelled as data. Person-owned revisions are checked by hash and reversible as described below; skill evaluations and retirement are not built. Tests: `packages/platform/test/memory-store.test.ts`, `packages/platform/test/memory.test.ts`, `packages/platform/test/codex-plugins.test.ts`.

## Built: a plugin's commands, agents and hooks

Built in `packages/platform` (`src/memory/plugin-parts.ts`, `src/composition/memory.ts`, the `agent` of `start_child` in `src/composition/parallel-work.ts` and `modules/harness-pi`) and the app (Settings, "Plugin commands and agents"; the composer). Two sources, each part marked with its `origin`:

- **Claude Code plugins** (`origin: claude`): the same enabled installs as plugin skills, in the layout Claude Code documents (code.claude.com/docs/en/plugins-reference, read 5 November 2026): `commands/*.md` and one level of subfolders (a slash command: front matter, then a prompt template), `agents/*.md` (a sub-agent: `name`, `description`, `tools`, then its instructions), and `hooks/hooks.json`. The `commands`, `agents` and `hooks` that `.claude-plugin/plugin.json` declares are honoured as documented: `commands` (a path, a list of paths to `.md` files or folders, or an object of name to `source` or inline `content`, with its `description` and `argumentHint`) and `agents` (`.md` files only) replace the default folders; `hooks` (a `.json` path, an inline object, or a list of either) add to `hooks/hooks.json`.
- **Codex plugins** (`origin: codex`): Codex's own installs, read only, in the layout Codex documents (developers.openai.com/codex/plugins/build, read 5 November 2026): `$HOME/.codex/plugins/cache/<marketplace>/<plugin>/<version>/`, used when `$HOME/.codex/config.toml` has `[plugins."<plugin>@<marketplace>"] enabled = true` (only that table is read). Codex also documents a repository's `.codex/config.toml` enabling or disabling a plugin for that project, loaded only for projects Codex trusts, closest folder winning and overriding the person's own config (developers.openai.com/codex/plugins/build, read 5 November 2026). That layer is not read: Backbone's plugin discovery is per person, not per project, so honouring it needs project-scoped discovery for skills, plugin parts and connectors, and a reading of Codex's trust record. Without it a plugin enabled only in a project is not listed, and a project's `enabled = false` does not hide a plugin the person enabled; either way nothing is used until the person enables it here. Hooks come from the root `plugin.json`'s `extensions["com.openai"].hooks`, else `.codex-plugin/plugin.json`'s `hooks`, else `hooks/hooks.json`; a declared value replaces the default file, as documented. Codex documents no commands or agents in a plugin. The installed Codex plugins observed on 5 November 2026 (codex-cli 0.165.0) carry them in Claude Code's `commands/` and `agents/` folders, so those two folders are read; a Codex manifest's own commands or agents paths are not. Codex does not document which of several version folders it uses, so each present is read. A plugin or marketplace name that is not a plain folder name, and a version folder that is a link, are skipped.
- **Declared paths stay in the plugin.** A path a manifest declares must start with `./`, contain no `..`, go through no link (one pointing back inside is not followed either) and resolve, after realpath, inside the plugin's own folder; files are then read from the checked handle as every plugin file is. A path that fails any of this, is missing, is the wrong kind (a folder for an agent, a non-`.json` hooks file), or cannot be read safely is listed as `refused` with why, cannot be enabled, and nothing of it is read. A refused part's declared path is plugin text and passes the same credential check as every other field.

- **Offered as a found SKILL.md is.** Each is listed (`plugins.parts`, `PluginPart`) with its plugin's id and its text's SHA-256 (`digest`), and used by nothing until the person enables it (`plugins.decide`). Enabling names the digest they were shown; a file changed since is refused (`STALE_BASE`) and listed anew, and the shown text is what is pinned in `skills/.plugin-parts.json`. Once a part's text is seen to differ from its pin, the permission is removed for good, checked before anything else about the file (a change that also makes it invalid still ends the permission): the old text coming back leaves it off until they enable it again. A permission is for one part: its id names the part's origin (Claude Code or Codex) and kind (command, agent, hook) as well as its file or manifest entry, so a file a manifest moves from `commands` to `agents` is a new part, off until enabled (permissions recorded before 5 November 2026 were keyed by file alone and read as off). A permission whose part is no longer read, because it is now refused, unreadable, a link, moved or removed, ends the same way: its pinned text cannot be checked, so the old text coming back leaves it off. If that removal cannot be written, the host keeps it for the life of the process and treats every plugin command and agent as off, saying why in Settings, until a write succeeds. Front matter enables nothing.
- **Credentials.** Every field that leaves the host (plugin id, name, file path, description, argument hint, declared tools), the strings Settings and the composer join from them, the raw file, and the plugin's manifests (raw, and every key and string decoded from them, so one written with JSON escapes is found) are checked against the stored credentials and credential shapes, and against each stored credential with whitespace and `,` `;` `|` taken out of both, so one split across a list is found. A part holding one anywhere is listed with every field of its own withheld and `blocked` saying why, cannot be enabled, and is never offered or used; the assembled words given to a model (the agents offered, an agent's role with its brief, a filled command) are checked whole as well. When the stored credentials cannot be read, every field is withheld and nothing is enabled. A name a model gives for an agent or command is never said back in a refusal ("No enabled agent by that name").
- **Commands.** An enabled command is typed in the composer as `/name <words>` (or `/plugin:name` when two share a name). The host fills its template (`plugins.command`: `$ARGUMENTS` all the words, `$1`…`$9` each, a quoted one whole; words the template does not name follow it as `ARGUMENTS:`), and the composer sends the result as the person's message, at their own settings. Typed while a turn runs, it is filled the same way whether it waits for the turn (`queue.add`) or reaches it as a steer (`turns.steer`). Its `allowed-tools`, `model` and shell lines (`` !`…` ``) are kept as words: nothing is permitted, chosen or run.
- **Agents.** A turn is told, beside recalled memory, the name, plugin and description of each enabled agent. `start_child` with `agent` set to one's name puts its instructions ahead of the brief as the child's role, said to be a plugin file's words that gives no permission, with its declared tools named as not permitted. The child is started as any brief is: settings narrowed from the parent's (a reviewer stays at `ask`), a mandate delegated from the parent's run, its brief told as an agent's words. The agent's `tools`, `permissionMode` and `model` change none of it. One not enabled, or changed since, is refused by name and no child starts.
- **Hooks.** Hooks execute commands on the person's computer, so each event a plugin hooks is listed as `not-run` with "Not run: hooks execute commands; Backbone does not run them" (the app names itself by its brand; the platform's own words say "this app"); it cannot be enabled, and no code in this path starts a process.

Accepted limits: a same-user process that swaps a folder above a plugin file for a link between the reader's individual calls can still win the race. Node has no `openat`, so each check is by path; after the read, the open handle must still be the file the realpath names, inside the plugin folder, and every inode check uses `lstat`. That refuses a link held for the open and `stat` calls and undone for each `realpath` and `lstat` (the interleaving `plugin-parts.test.ts` simulates), but not a swap timed between two single calls of the same kind. This is the same boundary as the engine's bare preflight, the export folder and the plugin README: a process running as the person can already read their files. An enabled command or agent is plugin text that becomes model input (the person's message, or a child's role) and can steer within what the turn may already do. Credentials are found as written, not decoded: a plugin whose text already carries the person's credential in an encoded form (base64 or similar) is not detected. Outside egress stays closed, so a model given it cannot send it anywhere. Tests: `packages/platform/test/plugin-parts.test.ts`, `packages/surfaces/app/e2e/plugins.spec.ts`.

## Built: skills that learn from use

Built in `packages/platform` (`src/memory/skill-learning.ts`, `src/composition/memory.ts`, the daily hook in `src/composition/proactivity.ts`). Nothing it makes is active until the person accepts it, and it deletes nothing.

- **Drafting on its own.** After a finished turn that was complex (done, at least three tool steps, at least one document written, every write DONE, no failure, refusal, withheld read or unknown outcome) a skill is drafted by the same mechanism as `skills.draft`, from the turn's request, steps and answer, with the documents it was given as its sources, under `skills/.proposed`. The engine's step labels and answer are quoted line by line under "Observed in one run", as data to check, not as instructions, and the Memory page shows the whole draft (`Skill.body`) before Accept. Either drafting path takes a name no skill in the data folder has in any state (`name-2`, …), and sources are only ever joined, never replaced, under the data folder lock, recorded before the text is written and removed if it cannot be. At most one a day per project (local day), none from a host-written schedule or goal turn, and none when the person turns it off (`skills.learning.put`, `MemoryView.learning.auto`, on by default). A refused draft (credential) does not use up the day. It is told through the daily brief as a pending item, never at once (C3).
- **Corrections.** When the person's message is a correction (memory's own rule: "no, …", "actually, …") and the turn before it in the chat shows it used one of the data folder's accepted skills (its steps or answer name the skill; being offered it is not enough), an edit is proposed: the skill's text with the correction added under "## Corrections", held under `skills/.edits/<name>` with a line diff (`Skill.state: 'edit'`, `Skill.edit`), and told in the brief. It is refused if the edited text holds a credential, records the sources of both turns (`edit:<name>` in `skills/.sources.json`), leaves on their withdrawal, and is accepted (`skills.decide`, under the data folder lock) only onto the exact text it was made against (`STALE_BASE` otherwise); the skill takes on its sources before its text changes, and only then does the edit's record go. Skills in the person's own folders are never edited.
- **Review, editing and undo.** The Memory page shows the full draft and links to its source chat and finished turn. Source turn IDs live in `skills/.origins.json`, separate from the editable Markdown. `skills.put` changes a draft without accepting it, or edits an accepted data-folder skill, using the revision hash shown to the person; a later outside edit refuses the save (`STALE_BASE`). The name stays fixed and the description is required. Before an accepted edit, including a correction accepted through `skills.decide`, `skills/.history.json` durably keeps the earlier text, expected replacement hash and source dependencies (last 50 changes). `skills.remove` moves an accepted skill to the existing archive and records an undo; it deletes no bundle files. `skills.undo` restores the text or folder only while the current version matches the recorded outcome, checks credentials again and preserves later human edits. The Memory page offers undo only for the current matching version; an interrupted replacement leaves either the old text or a matching recoverable change. Undo retains the union of source dependencies. Undoing removal starts the same unused-time grace period as Restore, so the curator does not immediately archive the skill again. Corrupt or unsafe optional history/source-turn records leave the Memory page usable with a notice. Mutations refuse to overwrite unreadable recovery records. Withdrawal discards unreadable snapshot records (or their terminal links) before continuing the independent skill-folder purge; it never follows a linked target or removes an unexpected record directory. Failed record cleanup is reported as pending after other removable skills are purged. Withdrawal removes snapshot words before ordinary source records are cleaned; a withdrawn snapshot cannot be restored. These controls never edit skills in the person's other agents' folders. Tests: `packages/platform/test/memory-controls.test.ts`, `packages/surfaces/app/e2e/memory-controls.electron.spec.ts` (installed execution belongs to the stack gate).
- **The curator.** Run once a local day by proactivity's tick, or on demand (`skills.curate`), under the data folder lock. It moves each of the data folder's own active skills not used, accepted or restored for 30 days (by its usage record, else its file's change time), and with no edit waiting, to `skills/.archive/<name>`, where it is listed as `archived`, given to no turn, still purged with its sources, and restored with `skills.decide` `restore`. It proposes merging two active skills whose names and descriptions share at least three words and 60% of all their words (`MemoryView.learning.merges`); it merges nothing, and a merge the person declines is not proposed again. What it did is told in the daily brief.
- **Usage.** After each turn, `skills/.usage.json` records by name each skill it was offered, and counts it used when that turn finished done and its steps or answer name it.
- **Provenance through skills.** A turn offered one of the data folder's skills inherits that skill's sources as reads, as it does a remembered line's, and only a skill whose sources were recorded is given; so a draft or edit from that turn records them, and a withdrawal reaches what was derived. A turn whose sources are not all known drafts no skill, by hand or by itself: the skill would record no source a withdrawal could reach.
- **Files.** Every write, move and removal under `skills/` (`.proposed`, `.edits`, `.archive`, the active folders and the records beside them) goes through `safe-read.ts`'s anchored writers: each folder from the data folder's `skills/` down is a plain folder at exactly its expected real location, checked again after the write or rename; a link fails closed, and the curator moves nothing outside `skills/`.
- **Purge.** A withdrawal's purge first takes the purged skills' names (folder and front-matter) out of the usage record, the merge proposals, the learning record and the daily brief (pending or delivered); then removes their folders; and only then their source records, and only where that cleanup and every removal went through. A folder that could not be removed (a linked parent, a failed removal) keeps its record, so discovery, restore included, still hides it, and the next purge or the daily curator tries again. A draft's or edit's brief line is added under the same data folder lock as its record, after its sources are checked again; a turn's usage is not recorded for a skill whose source has since been withdrawn; stored merge proposals are checked again (credentials, skills present and intact) before they are shown. Merge names and shared words are checked for a credential before they are stored or shown; a pair holding one is not proposed, and the curator does not run when the stored credentials cannot be read.

Accepted limits (cold review, round 2):
- Paths under `skills/` are checked before and after each write, move and removal, but Node has no `openat`: someone who controls filesystem entries in the data folder can still swap a checked folder for a link in between (a pathname race). It is not reachable through document text alone.
- An accepted skill can carry quoted text an injection shaped. The quotes are labelled as data observed in one run, and the whole draft is shown before Accept, but accepting it makes that text reference material given to models.
- "Used" means the turn's steps or answer named the skill; the engine does not report whether it followed it.
- Draft acceptance takes the data folder lock, with no test that fails without it. Merge is advisory: the person merges by editing. Near-duplicates are found by shared words, not meaning. Tests: `packages/platform/test/skill-learning.test.ts`.

## Saved helper roles

Person-authored Claude Code subagent Markdown roles live in <data folder>/.agent-roles, outside the skill namespace. Legacy files in skills/agents migrate automatically only when there is no SKILL.md and no skill-source record for that folder. Eligibility requires a plain, single-link, valid-UTF-8 Markdown file that parses as a role and whose file name matches its role name. Current credential checks cover raw Markdown and decoded role fields before any canonical or recovery copy. Copy verification precedes removal. A different canonical definition is kept, with the independent legacy bytes saved under a digest-based recovery name in .agent-roles/.legacy. Per-name migration records prevent deleted roles from reappearing after later legacy edits.

A shared skill folder cannot establish independent role ownership from Markdown syntax alone. Parseable role-shaped references are not automatically activated or copied into recovery outside their skill provenance. Only cleanup and curation of skills/agents stay pending while such ownership is ambiguous; every other eligible skill proceeds. The ambiguous files and their source records remain in place, hidden from recall when withdrawn. The daily brief and Settings report the folder for manual review. The initial withdrawal takes effect immediately and finishes independent cleanup before reporting any remaining cleanup as a failure. A repeated withdrawal retries the same purge under the home lock before returning success; pending records still refuse completion, and a successful retry does not repeat the withdrawal effect. An explicit role save establishes ownership for that exact definition version, allowing its matching legacy copy to follow normal skill cleanup without affecting the independent role. Ordinary readable references without role-shaped front matter remain skill-owned and do not block cleanup. Known skill reference subfolders are never migrated as roles and are purged normally with their sources. Unreadable, invalid-UTF-8 or oversized candidates, invalid role-shaped front matter, and unrecognizable edits of previously migrated roles also protect only that folder from destructive cleanup until reviewed. Nothing unclassifiable is silently copied or deleted.

Each listing or migration pass examines at most 64 directory entries plus one metadata lookahead, with candidate files capped at 32 KB. The skill-source index is read with a 1 MB cap; an unreadable or invalid index leaves ownership unproved. Settings reports when discovery stops at 64 directory entries, with a typed refusal if migration or listing cannot be read safely. Turn recall catches migration failures and continues with available memory and canonical roles; admission reads only the selected role and checks current credentials after any migration lock wait. Oversized or ambiguous legacy directories can require manual ownership review before purge/archive. Forks are ordinary chats: helper role tool limits do not carry over, and both fork actions state this. A denied write remains refused when an engine failure coincides, with the failure preserved in the turn and displayed in the answer; unknown outcome and interruption keep priority.

Threat note (review L3): a process already able to write this person's data folder can edit or add role definitions, as it can skills. Such files can supply instructions and choose a served model, but cannot permit tools, permissions or a provider route. The existing same-user pathname-race limit above also applies to role migration.

Follow-ups: add the host-level L6 regression proving that a reviewer whose role lists Write stays read-only (the tool-host intersection test covers unavailable Bash/connectors); add guided ownership review for ambiguous legacy files and pagination beyond the listing cap, which remains separate from explicit-name admission. Canonical role definitions are exported in full as numbered Markdown files, with the normal credential scrub and safe reads. The outgoing redacted definition is checked by the same role parser, including decoded YAML fields; an uncheckable definition refuses the whole export before anything is published. Import restores them as inactive reference documents under Restored history, never as active instructions; the person can inspect and save an intended definition in Settings. Migration markers and recovery copies remain local. These are not installed-app acceptance claims; that journey is proved by the stack gate's installed suite.
