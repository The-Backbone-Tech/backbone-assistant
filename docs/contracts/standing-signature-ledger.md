# Permissions in the decision ledger

Owner: Core decisions and ledger; connector consumer: platform. This section specifies the additive permission crossing. Focused Core, upgrade, connector and whole-Host tests qualify the implemented paths; automatic owned-open installation is now wired after verified material enforcement. Independent review of bd3f8a6 accepted with fixes; the follow-up changes below address those findings.

## Existing links and installation boundary

A decision identifies its subject through `(workspace_id, subject_kind, subject_id)`. For an effect, subject_id names app.effects.id. A connector effect has a connection_id resolved by gov.propose_effect from the second component of its mcp operation and app.connections.slug. The complete operation is `mcp.<slug>.<tool name>`; effects.tool is the calling carrier's tool label and need not be the connector tool name. The permission must therefore bind connection_id and the complete operation reconstructed from the connection's immutable slug and the registered connection_tools.name. Match the complete operation, including any dots in a tool name, rather than splitting out its third component. The Core has the registered tool name and input schema, but not the platform's complete description/annotations/seal digest. That digest is opaque evidence; the Core cannot independently detect an unreported definition change. The platform owns that invalidation.

The baseline is assembled from one SQL file per object in packages/core/schema/baseline.json by buildBaseline. Released material guard, link and enforcement installers select pinned baseline statements, install in one transaction under CORE_SCHEMA_LOCK and attest exact catalogue profiles. Their function pins include the four-argument answer and its settle helper. Neither released function may change. Append one self-contained permission step after enforcement; preserve all prerequisite profiles. Generate new source pins with a project script.

The installer for owned personal data folders is explicitly wired in packages/core/src/db/personal.ts. Its external branch only verifies; its owned branch runs the three material installers and then upgradeSignatureLedger on the owned installer connection only when materialEnforcement.state is verified. There is no generic step runner or hidden installation through a material installer. The connector performs its own read-only verification of the receipt and exact profile, including on external data folders, so no new CoreLink status is necessary. When the step is unverified, giving permission and tool permissions return a plain refusal receipt with update instructions; the held action is unchanged. Per-call permissions and discards use the released four-argument crossing and work unchanged. A standing approval never falls back to that crossing, including after a transient failed inspection between successful checks. When verified, the new crossing records structured basis.

## Permission life and answer basis

The person, outside every run, gives one permission through gov.give_connector_signature(connection UUID, registered tool name, opaque definition SHA-256). The Core generates and returns a fresh UUID. It appends signature.given through gov._append while holding the workspace lock. The ledger stores sec.digest of the opaque definition digest, never the caller's unkeyed digest; the private store and the platform retain their own binding values. An indexed workspace/id record stores its person, connection, tool, complete operation, digest and end status. gov.end_connector_signature accepts only that same person outside runs and a fixed reason: person_revoked, definition_changed, connection_removed, home_moved or superseded. Ending is terminal and idempotent; giving never accepts a caller-selected UUID, so an ended id cannot be replayed.

A separate gov.answer_decision_with_basis crossing takes the released answer's arguments plus a JSON basis: person, or standing_signature and its UUID. It rejects extra fields. The ordinary decision checks and workspace/decision locks remain. A standing answer requires approval of a connector effect, a live permission given by the same person in this workspace, exact connection_id and complete operation equality, and a registered tool whose removed_at is still NULL. It cannot approve a promotion or elevation. All refusals leave the decision, effect and ledger untouched. The answer appends decision.answered with basis as structured JSON through a separate settle helper; the released functions remain byte-for-byte unchanged.

The installer locks app.workspaces against concurrent creation, then appends decision.basis_enabled to each existing workspace under its head lock. It refuses a pre-existing boundary without its migration receipt, rather than appending a second boundary. An answer with no basis before this marker reads as basis_not_recorded; one after it is classified from its ledger actor, never assumed to be a person. Workspaces created after installation have no old answers and need no marker: a missing basis there is classified from its ledger actor. No history is rewritten. Audit readers can reconstruct this distinction from ledger rows alone. The new crossing explicitly records person for per-call permissions.

## Two approval settlement paths

There are two approval consumers. The released gov._settle_decision in packages/core/schema/gov/_settle_decision.sql consumes answers from the released four-argument gov.answer_decision and gov.verifier_answer. The additive gov._settle_decision_with_basis in packages/core/schema/gov/_settle_decision_with_basis.sql consumes the checked answer and structured basis from gov.answer_decision_with_basis. Both settle the decision, remove its verification queue entry and append decision.answered. For an approved effect awaiting its checker they allow and enqueue it (with the class-4 delay), then wake its run; for an approved promotion they accept the candidate as knowledge through gov._promote; for an approved elevation they apply the catalogue classification through gov._apply_classification. Rejections deny the effect or reject the candidate/change instead.

The additive copy already delegates ledger append, effect enqueue, run wake, knowledge promotion and classification to the same released private helpers: gov._append, gov._enqueue_effect, gov._wake_run, gov._promote and gov._apply_classification. No smaller released helper owns the remaining decision update, queue removal and subject dispatch. Calling the whole released settle helper would append an answer without the checked basis; changing that helper would violate its released exact pins. Therefore its remaining code stays duplicated, with only the function signature and basis in the answer payload differing. No released helper or pin is changed.

The later closure unit is expected to route both consumers through one approval recheck function. The comment at the top of the additive SQL marks the single insertion point: after reading the decision and before updating it. Installing a guard in only one settle path is insufficient. Knowledge promotion already shares gov._promote and its source guard; later approval checks must cover effects and elevations too wherever applicable.

## Platform paths, order and recovery

The current service gives a permission only in ConnectorService.set. It ends permissions in closeDoor (server disabled, changed fingerprint, closed egress and revoked/missing plugin), refresh (changed or removed tool), set (override changed, tool disabled, explicit end, replacement), and signed's validity checks (data folder moved, changed launch/account/seal/definition). A launch/account mismatch still suspends the permission until exactly what was signed returns. Moving the data folder or removal from discovery now retires it during reconciliation; this conservatively includes an unreadable/missing configuration. Viewing alone does not mutate the file.

Giving: Core first, then connectors record with the Core UUID. If interrupted before the Core commit there is no usable permission; after that commit but before file persistence there can be an unused Core permission, never unrecorded platform authority. Do not repeat a give blindly after a lost result. A retry gives a new UUID and ends any earlier live permission of the same person, connection and tool as superseded in that same Core transaction. If a give commits before an undelivered pending end reaches the Core, the Core can see only its own live permission and records superseded. The later end is a terminal no-op, even if its local pending reason was person_revoked or definition_changed; the earlier reason was never delivered to the Core and is not reconstructed. A partial unique index enforces at most one live permission; old given/ended rows remain audit evidence.

Ending: durably remove authority in the connectors record and retain a pending end (UUID and enumerated reason) in the same file write; then end it in the Core; then remove the pending end. Retry pending ends before using permissions. Failure or interruption cannot reopen the local door. Core end is idempotent. A not_found end is dropped as already absent; a someone_else end is dropped from the retry queue and recorded locally in signatureEndConflicts with its UUID, reason, observation time and outcome. No Core end is invented for that conflict. Other failures remain retryable. If the step is unverified, pending ends remain locally closed without blocking per-call work until installation. The deciding guard covers ready() failures too. A superseded permission follows the same terminal path.

Legacy permissions: remove them at first reconciliation and require the person to sign again. A local legacy UUID is never asserted to be a Core permission. New permissions carry an explicit Core-version marker and are still checked by the Core at the answer crossing. This avoids inventing the original person's identity, time or intent. A moved data folder closes its permissions and journals home_moved; no copied authority becomes usable.

On the integrated base, the connectors record, pending-end queue and conflict record pass through assertHomeWriteAdmission for both the data folder and its connectors directory before their durable save. Permission changes and pending-end processing check this admission before Core crossings too, so an unsupported connector submount cannot consume a permission or end. The data folder lock protects file order; the Core workspace lock protects permission and decision order. A new asynchronous file mutation must recheck the existing file version before saving. An overtaken Core-first give can leave an unused Core row, but must never overwrite a later end. The platform's stored approval remains only a recovery hint; it cannot supply an unchecked basis to the Core.


## Core startup and the data folder lock

Connector mutations request their Core link before acquiring withHomeLock. Removal gives an already available link one event-loop turn, then proceeds locally even if the link rejects or never settles. Its pending end is retained; a late link schedules a drain through outsideHomeLocks. Closed services do not start late drains. Giving requires a link within two seconds and otherwise returns the plain unavailable receipt before changing the connector record. Core verification, give/end and decision read/answer crossings run outside the data folder lock. A give is computed from locked local choices, committed in Core, then persisted under a fresh lock only if the file version still matches. An overtaken give leaves an unused Core row and recomputes the local mutation instead of overwriting newer choices. Ending saves local closure and its pending end together before waiting on Core; the drain takes a fresh lock only to remove a confirmed pending item after its version check. Purely narrowing settings still skip credential preparation, and opening a door remains local consent; an actual send requires the Core's checked answer.

Resolve rereads Core outside the data folder lock, then locks only to choose and synchronously persist the immutable approval word. It answers Core after releasing the lock. Core verifies permission life in its own transaction; send rechecks the same local permission after every wait, so a concurrent end cannot dispatch a call. Both hold and resolve check admission for the data folder and connector storage at entry, before proposing or answering. Tests instrument Core reads and calls to reject an active data folder lock scope, and narrow local authority during a give to verify that the tentative Core permission is not persisted. The whole-Host restart controls for pending ends, a removed server, a lost give reply and an empty data folder remain covered.

Reads are observations, not reconciliation: connectors.list calls only list(), including on a writable Host. Legacy permissions are reported inactive; they are retired on writable startup or the next mutation. Pending ends are delivered there, never by a read-only Host. The other inspected reads are offered(), doorView()/doorSeal(), toolView(), readNeedsAsking and used; their signed/stamp helpers read an existing valid seal key without repairing or creating one. A missing or invalid key suspends authority and returns no door/tool confirmation view until a writable enable initializes it. Discovery and revocation caches may narrow in-memory visibility; these reads write no data folder bytes and make no Core query. Tests compare complete data folder files and count Core reads on read-only legacy/pending data folders, then verify the first writable startup retires/drains.

The seal-key write now checks data folder and connector-directory admission immediately before writing. Read helpers still use only an existing valid seal key, and never create or repair it.


## Qualification and remaining integration

The focused Core tests exercise a tool name containing a dot and a carrier tool label different from the connector tool. This discriminates complete operation binding from an incorrect third-component or effects.tool comparison. They check the hash chain, immutable ledger rows, service table-write denial, generated UUIDs, terminal and idempotent ends, strict basis shape, ordinary checker/proposal guards and two concurrently valid answers. The concurrency test observes the second backend blocked on the first before committing; it does not infer order from a sleep.

The mutation obligations are mapped to the named cases in packages/core/test/signature-ledger.test.ts:

| Case | Mutation the assertion detects |
| --- | --- |
| real/invalid run giving, ending and answering | remove the first names_run refusal; the fallback role/no_identity reason also differs |
| agent/system/empty identity | remove person-kind or identity checks |
| another person's permission | remove person_id equality |
| ended permission | remove ended_at refusal |
| another tool or connection | remove the connection_id/complete-operation binding |
| random UUID | remove the NOT FOUND refusal |
| another workspace | remove workspace isolation (lookup predicate and forced tenant wall are independent defenses) |
| replay after end | revive the ended row or permit caller-selected identity; service UPDATE is also denied |
| competing answers | remove open-status/serialization protection; the second answer must never replace the first basis |
| nonconnector/noneffect decision | remove connector subject eligibility; each subject guard has its own case |
| changed released answer body | replace its RETURN with NULL; both old guard and new profile must pause |

These are discriminating negative cases and an executed fingerprint mutation, not a claim that a full mutation campaign ran. Removing only one of two redundant workspace walls need not make an attack succeed; the required check is their combined authority boundary. The connector's read-only verifier checks the new exact profile and receipt before giving, ending or answering with structured basis; merely finding the SQL function is insufficient. A mutation replacing give with a UUID return and no append is refused before any local permission is written. The catalogue mutation cases additionally cover definer posture, permissions, forced RLS, immutable-column trigger and primary-key constraint. Source admission rejects a changed end-status refusal before DDL.

Platform fault injection uses the existing CoreLink proxy style and the durable writer's emit boundary: before give, after committed give/lost reply, after give file, after end file, before Core end and after committed end/lost reply. Reopening keeps authority absent or tied to the existing given row, drains pending ends once and verifies the ledger chain. Existing connector send/approval race tests remain unchanged and pass.

The whole-Host test reads only app.ledger for its reconstruction: one given permission, three answered/dispatched/observed successful effects under its UUID, one person-basis effect, one ended permission and a later asked decision with no answer or dispatch. Surface state is used only to perform the person's permission, before reconstruction begins.

The frozen legacy baseline and every released additive prefix upgrade through the installer, retain the exact old answer row and keyed free-text note digest, and verify all prerequisite profiles. The personal-mode history now includes the permission step on the first owned open, with its verifier already verified before an explicit idempotent repeat. The owned-upgrade test opens a real cluster from each released prefix (zero, one, two and three material steps), closes it and lets an ordinary owned reopen install the permission step. Each then signs and sends one call under its Core permission and permits an unpermitted tool once as person; the ledger and its basis reader distinguish both. All four cases fail without the owned-open hook. The material-link actual-owned-open assertion is unchanged and passes with that hook.

The complete Core suite, full platform suite and heavy gates were not run because this task's final instruction permits focused tests only and reserves the heavy lock. The independent review of bd3f8a6 accepted with fixes; the follow-up commit series addresses those findings and remains available for integration review. No real data folder, provider, account or outside message was used.


## Readings of an answered decision

| Ledger evidence | Reading |
| --- | --- |
| Recorded standing_signature basis | The recorded UUID and standing_signature method |
| No basis, before this workspace's installation marker | basis_not_recorded |
| Explicit person basis or post-step missing basis; actor kind person | person |
| Post-step missing basis; actor kind agent and agent_role verifier | verifier |
| Worker agent, system principal, missing/unknown actor, or unknown basis method | not_stated |
| No answer row visible | SQL NULL |

Actor classification uses the row's workspace-scoped actor_id and principal metadata, including inactive principals, rather than the reader's identity or the decision's intended checker. The released verifier crossing remains unchanged. These distinctions preserve historical uncertainty while never labeling a machine answer as a person's answer.


## External data folders and installation

An external data folder supplies appUrl/operatorUrl for a database somebody else operates. The external branch of openPersonalDatabase inspects the earlier material steps but installs none of them, and it does not install this step either. There is no shipped external-upgrade command for those earlier steps or for this one; automatic external migration is a stated limit. The ordinary database operator role (backbone_operator) is not a schema installer.

The database administrator can use the exported installer APIs from @backbone/core/db on an administrative connection to that target database, with the current buildBaseline().sql: run upgradeMaterialGuard, upgradeMaterialLink, upgradeMaterialEnforcement in dependency order (require verified after each), then upgradeSignatureLedger (require verified). The installers select pinned statements, preserve the released profiles, serialize under the schema lock and record their receipts. Do not insert receipts directly or run only the new DDL. Reopen the data folder afterward; the connector verifies the new receipt and exact profile through read-only app connections. Until this explicit installation, external data folders keep per-call release/discard support, retire old file-only permissions and refuse permissions with instructions to update the Core or contact its operator.


## Additional integrity controls and redundant binding

The terminal trigger on connector_signatures is ALWAYS enabled and refuses clearing or changing an existing ended_at or end_reason, including direct governor writes. The table's immutable-column trigger still protects the original permission. A removed registered tool cannot answer under its permission even if platform reconciliation has not run yet.

The connection_id comparison in the answer crossing is redundant today with exact operation equality: within a workspace, connection slugs are unique and immutable, contain no dot, and the complete operation is constructed from that slug and the registered tool name. Two connections therefore cannot share this operation. It is retained as explicit defense of the stored connection identity if routing representation changes. No independent behavioral mutation claim is made for removing only this redundant half; the exact profile still detects that edit. The core: 1 test now observes signed() synchronously before ready() can retire an old record, so removing the marker check fails that assertion.

The permission step is not released yet. Adding the approval-recheck insertion-point comment changes the assembled source checksum, but no SQL function body or catalogue fingerprint changes. Review fixes may change this step's source pins, exact catalogue profile and checksum. Regeneration never changes the released material steps or their checksums, the released answer, or its settle helper. The separate settle helper intentionally duplicates the released behavior because modifying that released helper would invalidate its exact profile; only its new basis argument and ledger payload differ.
