# Backbone specifications

Short descriptions of product behaviour and cross-owner boundaries. They describe intent and proof questions, not a second backlog or evidence that a feature has shipped. Execution ([docs/execution.md](../execution.md)) owns current implementation, results and the queue; [Shape](../shape.md) owns properties; [Decisions and references](../decisions-and-references.md) explains choices.

| Work concerns | Start here | Acceptance owner |
| --- | --- | --- |
| Editable work, recovery, executor changes and consolidation | [Continuing work and artifact custody](continuing-work.md) | Existing material/engine contracts and installed continuity job in Backbone Next / Way |
| Choosing an approach for a task or a configuration for recurring work | [Solution selection](solution-selection.md) · [Worked company decision](solution-selection.md#worked-decision-a-new-company-workflow) | Backbone Way J-solution for task selection. The relevant product job qualifies the installed arrangement. |
| Authority, tools and external effects | [Authority, effects and recovery](authority-and-effects.md) | Kernel/lab contracts, actual Engine enforcers and the relevant product job |
| Supporting an existing company function | [Company context and work](company-context.md) | Backbone Way J-co and the relevant knowledge, integration and source owners |

Update the affected description when behaviour changes. Add a spec only when a shared explanation is useful; ordinary fixes can be clear from their code, task and checks. Keep private evidence and sensitive content with their actual owners. The [development guide](../development-map.md) helps locate source; exact thresholds remain in the owning acceptance contract.
