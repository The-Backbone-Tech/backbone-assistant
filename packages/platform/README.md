# Platform (L1)

The shared API and ports used by surfaces and modules, and the composition that wires them: the `api` the app calls (projection in, command out, receipt back), the Gateway the MCP door calls, and the Engine, ToolHost and ModelRoute ports an engine sits behind.
It depends on core and kernel, and composes Pi, mail and telemetry modules which also consume platform ports/API. It reaches the core through its `gov.*` crossings (`src/composition/core.ts`) and keeps a data folder: the core's embedded cluster, the work material's bytes, thread projections, sealed model credentials and a vault of the data folder's secrets whose key the Keychain holds (`src/keys/vault.ts`).

Channel tokens use the same sealed credential store through the trusted in-process export `@backbone-next/platform/credentials/channels`. It names Slack bot/signing and Telegram bot/webhook token kinds. The daemon and the person's CLI can store or resolve them with this data folder's vault keys; no Host API method or API line returns them. The [channel surface](../surfaces/channels/README.md) owns intake, binding and reply receipts.

**Audit export.** The read-only `audit.export` API produces versioned JSON Lines from committed
Core ledger entries and visible receipts, with content omitted by default. The CLI can export
while an app or daemon holds the data folder, or read a stopped embedded database from a temporary copy.
[Export the audit record](../../docs/how-to/export-the-audit-record.md) and the
[contract](../../docs/contracts/audit-export.md) describe the schema, commit-order cursor,
redaction, offline reader and coverage gaps. The record cannot say that a call went out under a
permission, nor when one was given or ended. Content is refused over every API line;
only a command opening an idle plaintext-key data folder can opt in. Export uses bounded pages, and
the CLI verifier reads incrementally. Default receipt anchors and private payload digests are keyed; published piece-file digests remain plain; raw opt-in commitments can confirm guesses of omitted values. Standalone scratch uses a checked per-user 0700 parent, also excluded from ACP restricted-agent reads; operator overrides require their own read exclusions. Stalled writes time out after 30 seconds, and holder sessions have a fixed two-minute lifetime.

Offline verification shows the file is internally whole. It does not prove the data folder's database
was unchanged before export, that all activity reached the Core, or that a destination received
an effect. Stronger evidence needs timely source ledger anchors and file digests retained outside
the data folder, independently protected permissions and trusted timestamps. This export alone provides
none of those external witnesses. There is no network sender in this unit. The focused audit tests cover redaction, paging,
cursor joins, canonical integrity, concurrent ordering, live-line disclosure, source-change/link
refusals, free-space refusal and cleanup under signals and failure; they do not inject every OS
I/O failure or qualify every platform.

Full/Custom in the Tool permissions screen is a renderer view choice. The platform
stores no setting for it: both views use the same existing per-tool permission
checks. The [remaining app dependencies](../surfaces/app/CONTRACT.md)
identify the listing fields and offline ending still owned by the service/Host
components. The online desktop ending channel is implemented.

## Use it alone

You need this repository installed (`pnpm install`). The platform runs headless: no app, no key and no network with the stub engine, which calls no model.

Fastest check: `node packages/platform/examples/try-platform.mjs` creates a host on a fresh data folder, makes a project, attaches a note, sends a turn, shows the agent's write going through the core's gateway, saves the result as the person, shows a stale save refused, then stops the database and removes everything. Its expected output is in [use the platform headless](../../docs/how-to/use-the-platform-headless.md), which CI runs.

The smallest recipe:

```js
import { createHost, removeDataHome } from '@backbone-next/platform/composition';
import { plaintextKeys } from '@backbone-next/platform/keys';
// A throwaway home's keys in plain text, chosen explicitly; the app passes the Keychain's (keychainKeys).
const host = createHost({ home, harness: 'harness-stub', keys: plaintextKeys() }); // or 'harness-pi', with a model route set
const project = await host.call('projects.create', { name: 'Q4 review', kind: 'folder' });
// material.attach, turns.send, threads.get, material.save … (the method map is src/api.ts)
host.close();
await removeDataHome(home);
```

Every method returns a receipt (`{ ok: true, value }` or `{ ok: false, reason, detail, outcome: 'REFUSED' }`); `host.on(listener)` streams events. The app carries the same method map over Electron IPC and an HTTP bridge (`packages/surfaces/app/server/bridge.ts`). The door's side: the MCP door calls `connectDoor` (`@backbone-next/platform/doors`), which holds no secret and relays to the host that holds the keys; that host serves the doors (`createHost({ …, doors: true })` in the app, `hostDoors` from `@backbone-next/platform/composition/doors` headless), each on `openGateway`'s logic over its own link. `grantDoor` and `revokeDoor` (`@backbone-next/platform/composition/gateway`) are the person's acts, run where the keys are.

The engine is chosen by `BACKBONE_HARNESS`, then the data folder's `settings.json`, then `harness` in the options, else the stub.

**Connecting AI tools to the door** (`tools.list` and `tools.disconnect` in the api; `Host.connectTool`; `src/tools/`). Connecting permits a permission, so it is not an api method and no transport carries it: only the process that showed the person the permission and took their click calls `connectTool` (the desktop app's main process, with a native dialog, as Docker Desktop's MCP Toolkit "Connect" and Claude Desktop's `.mcpb` install dialog confirm). Only a host given `tools` in its options manages tools; elsewhere, such as the browser bridge, they are refused. Detection is read-only and follows each tool's own variables (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `XDG_CONFIG_HOME`, `HOME`). `connectTool` takes the door's declared operations, ceiling and 30 days unless the person narrows them, and refuses anything wider; it permits a door named after the tool (`claude-code-1`, …) with `grantDoor`, as the person, never through MCP. Before a tool's settings change, a save point under `<data home>/tools/savepoints/` keeps each file's hash and a copy.

Every entry starts the door inside the app (`tools.door.command`), as VS Code's `code` command and Docker Desktop's MCP entries point into their app bundles, and names only `BACKBONE_HOME`. It is called `backbone-door`, distinctive as Docker's `MCP_DOCKER` is, so a `backbone` entry someone wrote by hand never meets it; beside an entry under that name that the app did not write, ours takes the next free name (`backbone-door-2`, …) and the row says so. Nothing is ever replaced.

Its own `modify` drops the comments between a removed member and the one before, so the placement of the one edit is ours (`test/jsonc.test.ts`) |
| Claude Desktop | a `.mcpb` bundle opened in Claude, whose own install dialog is the second confirmation; its config file is never written, and removing the extension is the person's step in Claude |

**Declarative, with finalizers,** as Kubernetes controllers and Terraform are. For each tool the data folder keeps what the person chose (connected under permission G, or taken back) in `<data home>/tools/state.json`, and a reconciler converges what is there toward it, both ways: at connect, at disconnect, at every start and after any failure. Each thing made adds a finalizer (revoke, entry, skills); taking a connection back runs them revoke first, and the record stays, shown as needing attention, until every one is done, so it never goes while its permission may be live. A connect that fails before it converges is taken back the same way. The reconciler also repairs drift: an entry removed by hand comes back, and one pointing at an old path of the app is rewritten to the door's new path. It never widens: an ended permission waits for the person, and after an update changes the door's digest the tool shows "Approve again" (the same one-click window) and nothing is permitted anew until then.

**Two apps, a crash, a restart.** Each tool's record is its own file with a revision (`src/tools/store.ts`), written by compare-and-set, never as a stale copy of everything; every change, and the door's own `grant` and `revoke`, holds an advisory lock per data folder (`src/composition/home-lock.ts`, on `proper-lockfile` 4.1.2, MIT: an atomic mkdir kept fresh while held), and the desktop app keeps to one instance per data folder (Electron's single-instance lock). A permission is asked for under an intent id the record holds first (the outbox pattern): the core keeps it on the mandate, so asking again returns the same permission (its run made then if it was cut short before it), a permission whose run or file never appeared is still found and revoked by it, a connect the app stopped in the middle is taken back at the next start, and a revoke counts only once the core says nothing for that id stands. The expiry the person approved is kept as an absolute time and reaches the core unchanged; an intent past it is never permitted. Tested in `test/tools-safety.test.ts` and `test/home-lock.test.ts`. (An earlier single `tools/state.json` only ever existed on the branch that built this and never shipped, so nothing reads or migrates it.) The usage skill (`src/tools/skill.ts`) goes to Claude Code's `skills/backbone/` and to `$HOME/.agents/skills/backbone/`, and is removed with the last tool that reads it. Tested in `test/tools.test.ts` with fake `claude`, `codex` and `open` commands in a throwaway data folder (`src/testing/tools.ts`).

**Why not Neon's `add-mcp`** (2.6.0, Apache-2.0, checked 26 Oct 2026). It writes entries for many more tools, removes them, and has a library API (`upsertServer`, `removeServer`). It writes every tool's file directly, `$HOME/.claude.json` included, where ours uses Claude Code's and Codex's own commands. It writes Codex's TOML with `@iarna/toml`, whose output keeps no comments, and its README documents dropping comments for one tool. It does not document what it does with an existing entry of the same name; ours never replaces one. Its six runtime dependencies are on caret ranges, from one maintainer, with a permission every few weeks. It does not beat ours on all of these, so the writers here stay ours; it is the reference when a second wave of tools (VS Code, Zed, Gemini CLI, Goose) is added.

**What the door's place promises.** The entry points into the app, which macOS code signing and App Management protect from other apps once the app is signed (it is not signed yet). A tool that runs unsandboxed as the same user, as Claude Code and Codex do, can still do much of what that user can: rewrite the app's files or the entries, or work on the cluster's own files (below). It no longer finds a password or a key in the data folder, and the door it starts holds none. The door bounds what such a tool does through it, not everything it does around it; containing the rest waits for the out-of-process sandbox and a separate identity for the database ([architecture](../../docs/architecture.md#pieces-in-the-hosts-process-the-trust-boundary)).

**Secrets at rest, and a door that holds none (design note, 26 Oct 2026).** The need: a tool running unsandboxed as the person (Claude Code, Codex, any script) must not read the cluster's superuser, service or operator password, the master key or a model key off disk, and the door it starts must hold none of them, with no Keychain prompt in normal use. What was weighed, checked on 26 Oct 2026:
- *Electron `safeStorage`* keeps one random key per app in the login Keychain, which other apps cannot load without the person's override; VS Code's SecretStorage and Claude Desktop (a `Claude Safe Storage` item) use it. Electron 45 deprecates the synchronous calls (removed in 46) for `encryptStringAsync`/`decryptStringAsync`, which also report a key rotation. The item trusts the app's code identity: an unsigned build is a new identity, so the person is asked again after each new build.
- *Our own Keychain items* with an access list bound to the code signature (a native module, as keytar was) bind to the same identity, and the data-protection keychain needs a signed app with an access-group entitlement. Neither gives more than `safeStorage`, and both add native code to build and sign.
- *An unsigned or ad-hoc dev build* gets `safeStorage` (the dev Electron is ad-hoc, linker-signed): secrets leave the files, which stops reading the data folder, a backup, sync, indexing or an agent's grep. It does not stop a process aiming at Backbone: without signing, hardened runtime and fuses, the app can be launched with `--inspect` or run as Node. Measured here: Electron 45 run with `ELECTRON_RUN_AS_NODE=1` hands JS `process._linkedBinding('electron_browser_safe_storage').safeStorage`, so with the RunAsNode fuse on, any same-user process runs code the Keychain takes for the app (Electron's fuses guide recommends turning it off; CVE-2026-70597 showed its same-signature parent check racy). Also measured: the unpackaged development build wraps with the login keychain's shared `Chromium Safe Storage` item (account `Chromium`), which every unpackaged Electron app on the machine reads; it asked nothing, first launch 3.8 s with initdb, second 0.7 s. A packaged app gets an item of its own (`Claude Safe Storage`, `Slack Safe Storage` and others sit in the same keychain).
- *Headless Node* (the door's CLI, tests) has no Keychain binding of its own; an item `security` creates trusts `/usr/bin/security`, which any process can run, so it is plaintext in disguise.
- *The door*: 1Password's CLI holds no vault secret and asks the running app over IPC, the app checking the peer (XPC with code signatures on macOS; on Linux a user-owned Unix socket any same-user process can reach, plus a setgid group check), with the person's approval.

**Decided.** The data folder keeps one vault, `keys/vault.json`: each secret sealed with AES-256-GCM under a data key, and the data key wrapped by what the caller holds (lab S22: an algorithm name on the wrapped key and on every entry). The desktop app wraps it with `safeStorage`; nothing else can unwrap it. The cluster's passwords reach PostgreSQL only as SCRAM verifiers, so no statement, log or file carries one. Tests and headless trials use an explicit plaintext vault (`freshDataHome`, or `BACKBONE_KEYS=plaintext`), which the packaged app refuses, as it refuses a data folder borrowing a test database. The door holds no secret at all: it relays its four gateway calls over a Unix socket to the one process that holds the keys (the app, or `backbone-mcp host` for a test data folder), as lab S18 asks of enforcers. The socket admits only the person's user (a 0700 folder) and carries only an existing permission's calls: no permission, revoke or other control. A bearer token would sit in the tool's config, readable by the processes it means to exclude, and a peer-signature check would prove only that our door relays, not who drives it, so the permission stays the authority. The door therefore needs the app running, and says so when it is not; an existing data folder moves its plaintext files into the vault once, at the next start.

**Built** (`src/keys/vault.ts`, `src/doors/`, `src/composition/doors.ts`; core: `openPersonalDatabase` takes a password keeper and makes no cluster without one). Proven by `test/keys.test.ts` (no file or log of a new data folder holds a password, the master key or a model key; a data folder in the old layout migrates once, stays readable, and finishes a move cut short with the same passwords; nothing opens without the Keychain's key; the app's keys refuse a plaintext vault and a borrowed test database; with no keys nothing is made; a stray `pg/pw` from an interrupted `initdb` is gone after the next open, migrated or not; the vault is written owner-only from its first byte and synced, with its folder, by the core's `writeDurable`; two model-settings saves at once both persist, since a save holds the data folder's lock for its whole read, seal, write and revoke), `test/doors.test.ts` (the door works through the host; the socket's folder admits no other user; a control call, a malformed line or a bad permission name is refused; with no host every call is `NOT_AVAILABLE`; a host gone mid-call is an unknown outcome, never a refusal; a second host leaves the first serving), `packages/surfaces/mcp/test/door.test.ts` (the door on a Keychain-held data folder: it works only through the app, and the person's commands without the keys are refused) and `packages/core/test/personal.test.ts` (SCRAM verifiers; no keeper, no cluster; a legacy move writes `cluster.json` durably before the old file goes and syncs the removal).

**What a same-user process can still reach.** Not a password, the master key or a model key in a file, and nothing through the door beyond its permission. Still: the cluster's own files (`pg/data`), so it can read every row at rest, or stop the server and start PostgreSQL in single-user mode on them, which asks for no password; the cluster runs as the person, and only a separate identity for it, or the tool's sandbox, closes that (lab S18, step 4). While the RunAsNode fuse is on, which the door's launcher needs (`ELECTRON_RUN_AS_NODE` on the app's own runtime), it can run code the Keychain takes for the app, and so unwrap the vault; until the app is signed with hardened runtime, it can also attach to it or rewrite its bundle. Copies made before the migration (Time Machine, APFS snapshots, backups) keep the old files. The app's window and the person's own permissions stay usable by any process that drives them.

**What is left.** Sign and notarise the app with hardened runtime, so the Keychain item binds to a stable identity (no prompt after updates) and other apps cannot rewrite the bundle. Move the door off `ELECTRON_RUN_AS_NODE`, to the app binary's own door mode (measured here: Electron 45 in its main mode relays stdio and imports the door's TypeScript, 0.7 s cold) or a small signed helper, importing only code inside the integrity-checked archive; then flip the fuses (RunAsNode, NODE_OPTIONS and inspect off; asar integrity and only-load-from-asar on) with `@electron/fuses`, a new dependency for ADR 0001. Linux and Windows wrap through the same `safeStorage` (a keyring is required on Linux; Windows DPAPI protects nothing from the same user, per Electron's docs). No door runs on Windows yet: the door and its host refuse there ("not supported on Windows yet"), because a named pipe's name can be made first by another user, who would hand out receipts; it needs a per-user name, an access list for the current user only and a check of the server first (`test/doors.test.ts`, `packages/surfaces/mcp/test/door.test.ts`). `e2e:installed` on an unsigned build is asked for the Keychain after each new build.

**Additional choice, 10 November 2026.** The 26 October judgement above is retained: a generic password created through `/usr/bin/security` is “plaintext in disguise” against an unsandboxed process of the same user. The independent scratch-keychain review observed such a process reading the item through that program without a prompt. The new system provider is offered for a different, narrower protection: a copied, synced or backed-up data folder, another unprivileged user, and a disk image whose Keychain cannot be opened without the login password do not contain a usable data key. It does not exclude any process of the same user that can ask `/usr/bin/security`. Compared with the app's safeStorage item, it deliberately gives up the app's code-identity access list; the measured unsigned-build and RunAsNode limits above still apply to that app protection. This is the person's choice: headless setup defaults to the system store, BACKBONE_KEYS=system requires it, and an explicit plaintext choice on an unprotected data folder exposes the data key in the data folder. No store failure chooses plaintext for them. The MCP host offers this now; the leased standalone CLI and daemon await their integration. These are two distinct protection promises, not a revision of the old measurement or judgement. Implementation, the selection table, Linux limits and tests are in [System keys](src/system-keys/README.md).

**Export and import of the person's work** (`src/composition/backup.ts`; `backup.export` and `backup.inspect` in the api; `Host.importExport`, never on the api; `exportHome`, `inspectExport`, `importHome`, `newHome`, `exportDestinations` and `rendererExport` from `@backbone-next/platform/composition/backup`). An export is the person's work as plain files: each project with every version of each document, each chat as history in JSON and markdown (what was asked, answered and written, never its custody, keys or links; a withheld answer stays withheld), memory and skills as markdown, the names and commands of their own MCP servers, and `history/receipts.md` and `.json`, a read-only report of every receipt the person can see (read as them, through the core's own policies), where an unknown outcome or held effect is marked unresolved: check before redoing. No database row and no authority: no permission, door, mandate, session, queue, claim, hash or lineage. Files and folders are numbered (`projects/p001/documents/d001/v1`), never named after what they hold. Every value the credential store holds is cut out of every string before it is serialised (keys included), and out of every document's bytes, with no length threshold; a stored value shorter than 4 characters refuses the export, since it cannot be cut out reliably; a last check refuses an export if any file or name still holds one, as written or as JSON escapes it. A file with a second name on disk refuses the export. Free text the person wrote is exported as written, and the README says so. The export is built in memory, then written into a new folder outside the data folder by its real path and renamed into place whole. A renderer never names the folder: Electron's main process and the browser bridge take only a one-time ticket their own picker issued, bound to the asking window (webContents id) and to the picked folder's device, inode and real path; that identity is checked again right before the export folder is made inside it and after it is written, and on a mismatch what was written is removed. A same-user process racing that folder is outside this boundary, and the README says so. The command line gives a path.

Import goes only into a new, empty data folder: `Host.importExport` holds the data folder's lock for the whole import and checks, under it, that the data folder has no project, chat, memory line, instructions or skill. It reads every file of the export once, into memory, while it checks it (a plain tree with no link, device or second name; only its own layout, compared case-folded and NFC-normalised; at most 512 MB; every file as its manifest says), and uses only those bytes. Through the host's own methods, as the person would: projects created, managed material restored with historical version labels and no Core author, ordinary originals attached and ordinary version histories added as the person's own (the host's internal `importDocument`, which no api method or transport reaches), every chat and the receipts report attached as documents to read, instructions put, memory lines put, skills proposed for the person to accept (internal too). Nothing is written as the database's installer and no table is written: the receipts are history, so nothing in them can be claimed, observed, sent or released. A withdrawn or hidden document stays out and says so. There is no replace: a data folder that holds work is refused and left as it is; the person imports into a new data folder and switches. Proven by `test/backup.test.ts` and `test/backup-boundary.test.ts` (no renderer method adds versions or proposes skills; no credential in a name, path, manifest or JSON escape, however short, and one too short refuses the export; an import uses only the bytes it checked though the files change mid-import; an export refused when the picked folder is swapped; an import refused into a data folder with only instructions or a skill), `packages/surfaces/cli/test/backup.test.ts` and `packages/surfaces/app/e2e/backup.spec.ts`.

Since round 4 of review: files the person attached are exported byte for byte, as attached (plain text aside); the credential scrub covers everything Backbone writes and every plain-text file, and the README and Settings say so. An export larger than the 512 MB a restore accepts is refused when it is made. Import is for `backbone restore` alone, into a new data folder the command line holds exclusively: `importExport` refuses a host that was used for anything that changes the data folder or has a call in flight, refuses every other call while it runs, counts any populated skill folder (`.archive`, `.edits`, `.proposed`) as work, and stops writing if it loses its hold on the data folder. The layout is exact names and case only, with folders as well as files checked for case-insensitive collisions; every reference (projects, document versions, chats, project instructions) is checked before the first write; memory lines come in through the memory import (`importMemoryText`: its front-matter and fence filtering, its 500-line limit and its source). Proven by `test/backup-boundary.test.ts`, round-4 cases.

Pieces are checked when they are loaded (`src/composition/pieces.ts`). Each loadable piece has an identity this composition fixes (`PIECES`), never one taken from the manifest it checks. Before `harness-pi` is used: its folder's manifest must name that identity, its digest is recomputed from its files (`src/pieces/digest.ts`, the algorithm `scripts/manifests.mjs` uses) and must equal the manifest's, and once the core is up that content must be a standing registration (`gov.register_piece`) that the person permitted (a mandate bound to it); only then is its module imported, and only from a read-only snapshot named by its digest (`<data home>/pieces/<sha256>/`, `src/composition/snapshot.ts`) that is itself checked against the registration. A module hook holds every file the import graph loads from the snapshot to the checked bytes, and refuses an entry or an import that leaves the snapshot or reaches a file the digest does not cover; each digest has its own module URLs, so an upgrade in the same process never runs a cached version. Dependencies resolve from the checked folder's `node_modules`, outside the digest. There is no static import. On a piece's first use in a data folder the host registers and permissions it as the person; after that, changed content is refused, and an upgrade needs the person to register it (`registerPieceIn`) and permit it (`grantPieceIn`, both from `@backbone-next/platform/composition/pieces`). Each Pi run is queued under that bound mandate and claimed with `gov.claim_run(…, 'piece', registration)`, so the core refuses any effect outside what Pi declares and any claim of a run bound to another piece; an interrupted turn is resumed only by the same registration. `grantDoor` registers the door's piece as it is on disk and permits the mandate to it; `openGateway` refuses to open a permitted door whose files are not that registration, so a new door version needs a new permission. A bundled app names the folders it ships with `pieceDirs` (the stub engine is part of the platform: its work is the recorded `'direct'` kind, under the person's direct mandate).

Snapshot publication first copies every checked file into a private writable staging directory, then atomically renames that complete tree to its digest-named destination. It verifies the destination against the registered digest and makes files 0444 and directories 0555 before import. Freezing follows rename because macOS 15 refuses to rename a directory already set to 0555. A reader can see the complete tree before permission finalization; it independently verifies the digest, finishes freezing (including after a publisher crash), and serves only the captured checked bytes. A failed rename counts as a competing publication only if the destination is readable and has the expected digest; otherwise the original rename error, including its code, is reported. Staging is removed on failure. This gives atomic content publication; permission finalization is recoverable, and does not replace content verification.


**Trust boundary.** A piece in the host's process is trusted, pinned code: the check above detects tampering at rest, not a hostile piece at runtime, and code in the process can undo it. The core's guarantees (mandate × declaration) bound only what reaches the core through a run's session. An in-process piece can reach the host's connection pool (the service role, which states any principal) and the vault the host opened (personal mode's database passwords, the superuser's among them, and the master key of the sealed model credentials), so it can act as the person or bypass the core entirely. An untrusted piece must run out of process, as the MCP door does ([architecture](../../docs/architecture.md#pieces-in-the-hosts-process-the-trust-boundary)).

**Mail triage: a named job, formed by one permission** (`src/triage/`, `src/ports/mail.ts`; the api's `triage.*`; `Host.signCapability`). The job `mail-triage` has two triggers, new mail (the connector's watch) and an optional schedule, and runs through the engine: for each request it reads the message through the gateway (a class-1 effect with a receipt, and the text recorded as an untrusted source, which marks the run), runs one turn of the engine whose only file is that message and whose only write is a triage note, then acts on the note in its own code. The note's category, urgency, label and move must come from the task's closed lists; the requester must be an address the message names in a header, a quoted forward or a form, never one in the prose; a reply becomes a draft held in the job's project as working material, addressed by this code to the requester alone (`workspace.write_document` through the gateway); a label or move is classified by the connector from the change itself and proposed. Its class (3) is above the capability's ceiling (2), so it waits in the brief for the person's one click: accepting answers the core's question bound to the change's hash; discarding refuses it for good. The mailbox's writes stay gated, so an accepted change waits unapplied; with a test connector whose writes are open, it is carried out once, and an outcome nobody can tell is settled by a provider probe (`gov.reconcile_effect`), never sent again.
- **Before formation** connecting permits a read-only mandate bound to the mail module: the job may read and classify, and the core refuses a draft or a proposal, with a receipt (safe without configuration).
- **Formation** (`src/triage/capability.ts`): the payload (capability id and version, tenant, plane, contract, owner, purpose, scope, tools, destinations and accounts, named classes, budget, absolute expiry, pinned model, engine, adapter and configuration) becomes the frozen intent of a root mandate, whose hash the core computes; the offer is shown with that same hash, and giving permission names it. Only the process that showed it calls `signCapability`, which no transport carries; the core permits a root mandate only to a person outside any run. A widening on any axis needs a new permission; narrowing becomes a child mandate the core keeps within its parent. ## Structured source input and restore

`material.attach` accepts an optional `relativePath`. With it, the exact logical path identifies an immutable original in managed storage; it creates no file in the project's physical folder. The Host records `MaterialEntry.source` as `{ kind: 'person', path }`: the person introduced this input, not necessarily authored its words. This identity gives no filesystem access, instruction loading, connection or effect. Without `relativePath`, the existing basename attachment behavior remains. An identical explicit source retry returns the same active original; different bytes, media type, case aliases or file/folder collisions refuse without choosing another name. A withdrawn or held original is not silently reactivated by a retry.

Every managed original is read into Core without an author, including explicit and restored inputs introduced by the person. Introduction does not establish who wrote the words. A connector's recorded origin takes precedence. The engine decodes an explicit original whose MIME is exactly application/octet-stream only when it is bounded UTF-8 (at most 2,000,000 bytes, no NUL, fatal decoding, BOM preserved). Other unknown MIME types, binary and invalid data keep the format placeholder; ordinary unknown formats retain their existing behavior. Dot-prefixed and native instruction-like names remain logical source data. The Codex adapter stages them under neutral numbered text names in a per-attempt inspection directory, with a manifest mapping their actual logical names, versions and classes. It never writes these inputs at their native autoload paths. The prompt identifies the inspection paths and manifest as data. Trusted snapshots separate that view from output proposals and verify every view file against Host-provided UTF-8 text copies: a modified, missing, extra or linked entry refuses that capture. An earlier validated stable checkpoint can remain recoverable if a later mutation is interrupted before the next capture. Logical names and versions remain unchanged in withdrawal checks and conditional import references. The raw target policy remains strict, so an agent must propose a revision as a normal working file; this view does not provide in-place editing of configuration targets, physical repository projection or universal prompt-injection containment. Ordinary source namespace, UTF-8 and resource limits still apply.

Exports containing managed material declare layout 4 and preserve logical names, managed projection and every version. Ordinary exports remain layout 3, and the reader accepts both. A layout-3 reader refuses layout 4 before restoring work. Layout-4 restore checks managed path syntax and namespace, ordinary basename validity, contiguous versions and source metadata before its first mutation. Managed documents restore first; ordinary labels retain their existing basename and alternate-name behavior around that namespace, including case-different flat labels. It creates new local material identities and requires exactly one immutable version for every original. Managed working histories become accepted documents and retain each version's person/agent label as history. All restored managed documents carry a Host-assigned restored mark and are read into Core without an author; archive labels never establish their trust. The restored mark protects only entries the archive declares managed. Ordinary non-managed entries in any archive, including layout 4, and restored chats and receipts are re-attached as the person's own and read as trusted. An archive is not signed: editing a document to remove its managed projection and source metadata, then resealing its manifest, presents that document as ordinary and bypasses the managed protection. Ordinary layout-3 behavior remains unchanged. A later person Save also retains the restored managed mark, so its version label alone still does not establish authorship. No old run, receipt, connection or permission becomes active. Declared server-origin metadata is not accepted as an active restore identity. The existing credential-redaction policy still applies to exported bytes and names. A malformed live managed label or a namespace made invalid by redaction can refuse the whole export; the refusal identifies the affected name with control characters escaped. Such material is never downgraded to ordinary to force restoration. Connector label admission and prompt/UI descriptions of historical authorship remain separate follow-up work.

The store writes a managed document's complete version set before its metadata commit. The Host retains the data folder lock for the import. This is not a transaction for the entire archive: an interrupted import may leave a partial data folder, and the existing empty-home rule then requires another new data folder. The export remains available. `test/structured-source-import.test.ts` covers input/replay refusal (including withdrawn and held originals), cold reads, origin precedence, strict source text, layout declaration, actual Host restore, layout-3 metadata injection and malformed metadata refused before mutation. A process crash between managed version writes and the metadata commit remains untested; the write-before-metadata ordering is verified by source inspection only.

Withdrawal delivery to Core starts from the store's durable withdrawal history. `MaterialStore.pendingWithdrawals` derives an immutable event identity from the material, project, withdrawal sequence, time and version; no separate enqueue can be lost after metadata commits. A local restore keeps earlier undelivered withdrawals. A writable Host starts delivery after opening succeeds and after a local withdrawal or restore. Local withdrawal returns without awaiting Core. The worker snapshots events under the data folder lock, delivers outside it and reloads metadata under that lock before merging an exact workspace/event/receipt acknowledgement. Save, restore and a later withdrawal therefore survive a delayed reply. Detached delivery leaves its caller's asynchronous lock scope before it queues for the physical lock.

The dedicated Core transport uses READ COMMITTED, checks logging before sending actor settings, and bounds connection, query, statement and lock waits. It acknowledges only after COMMIT returns. A lost response remains pending; retry sends the same immutable event to the idempotent Core crossing. One Host-owned pass runs at a time, with transient retries after 1 second, 5 seconds and then at most once every 30 seconds. It never repeats a provider operation. Only the crossing's stated conflict refusals are terminal; a generic uniqueness error stays retryable. A terminal payload conflict is retained separately from acknowledgement, stays pending in the durable history, appears in the project's Now notices and stops automatic delivery for that event. Both pending and conflict notices remain visible in a read-only Host. Closing cancels queued lock admission, stops retries, joins in-flight delivery and prevents a late reply from changing local metadata. Cancelling a queued admission preserves the predecessor lock and ordering of later holders; a lock acquisition already waiting on another process is joined before close finishes. This also avoids a close/open cycle when a door permission holds the data folder lock while waiting for the old Core to close. Import suppresses delivery and signals again after it ends. Transient failures remain pending under bounded backoff; one failed event does not prevent attempts for later independent events in that pass. A terminal conflict stays visible and does not block other events. There is no automatic conflict-resolution path.

Acknowledgements and conflicts are trusted composition methods, not public or model APIs, and are
not restored as active identities by export/import. A receipt tracks delivery only: it establishes
neither source authority nor Core's current state.

Typed file and MCP producers now verify exact material versions and preparations, retain observed
responses and register their Core bindings before handover. Pending connector observations stay
withheld; Stop and resume never register them automatically, and person-only reconcile/discard
preserves uncertain history without resending a provider call. Core enforces new material episode
bindings at validation.

Fresh decision, recall and final-use closure remains pending, and the temporary message/web guard
stays. The [connector contract](../../docs/contracts/connectors.md) owns these boundaries, including
the paused sql-v08 source-read path and portable restore lineage limits.

`test/material-withdrawal-outbox.test.ts` covers durable event identity and process kill after
metadata commit; `test/material-withdrawal-conflicts.test.ts`,
`test/material-withdrawal-delivery.test.ts`, `test/material-withdrawal-transport.test.ts` and
`test/material-withdrawal-host.test.ts` cover conflict retention, concurrency, bounded transport,
lost COMMIT responses and composed close/reopen/read-only behavior.

## Interrupted work and recovery data

Core close/open ordering is scoped to the canonical data-home path, including aliases. `CoreLink.open` snapshots only a pending predecessor close. Under an active data folder lock scope it refuses that dependency before claiming the data folder, opening the vault/database or writing any Core state. Mandatory turn snapshots and custody settlement continue to drain. A standalone person permission or revoke waits outside the lock and may retry this dedicated pre-write refusal once after unwinding its own lock. A nested caller must leave its outer scope; the tools service reports `NOT_AVAILABLE` and retains its pending revoke/configuration finalizers for recovery. Other errors, partial operations and unknown outcomes are never automatically retried.

A failed close remains observable to callers that captured it while pending. Its failure is retained and a fixed `CORE_CLOSE_FAILED` warning contains no original error text or credentials. Later opens inspect the data folder independently, later closes do not inherit a rejected predecessor, and the Host attempts to permit its ownership in `finally`. A fresh owner waits for prior permission attempts to settle and still probes the actual ownership socket; a recorded failure supplies no permission to bypass a live owner. Waiting for `hostClosed` joins the permission attempt even when the Core close failed.

A close registered after an open's snapshot is not awaited by that open, since that close may itself join the opener. Server shutdown can therefore still interrupt a person operation that has already begun; this residual is a partial/unknown failure requiring inspection or intent-bound cleanup, not permission to repeat it. A zero revocation count establishes only what that attempt revoked. Do not await a pending Core close or independently started Core/Host open while holding the same data folder lock: either may need that lock. An open invoked within a held scope can re-enter it, and its admission refuses a pending close. Host.close is idempotent, so repeating it neither closes the same link again nor registers another ownership release. The dedicated refusal, retry budget, alias handling, production tools caller, failed ownership release and preserved mandatory state are exercised by the home-close-order and tools-close-order test suites.

Recovery follows the original Core run, its receipts and its remaining authority. It never starts a replacement producer, resets a budget or blindly retries an unknown effect. A finished checkpoint stores pieces awaiting import; private custody binds a proposed document to its original bytes and source versions. Neither is proof that an output was authorised or completed. An acknowledged Stop discards unfinished checkpoint pieces, including after a restart, while recorded effects retain their original outcomes.

When the original run has ended or an import is definitively refused, unimported pieces can become local inspection copies. They carry `MaterialEntry.recovery`, stay hidden and held, and can be inspected or retired. They cannot become normal agent input, be attached to new work, be saved as an authorised output, or be activated by restore. A temporary import failure with no recorded proposal may end the old run and keep such a copy; it does not create another request.

After the explicit `Host.resumeInterrupted` step, transient checkpoint discovery or reconciliation read failures receive deduplicated retries with capped backoff. Each automatic attempt checks the original task and run again, reclaims only that run and settles its existing receipts and bookkeeping. It never starts a producer or proposes an undispatched write. The old run can therefore end as failed with its saved bytes kept as inspection copies, even when an uninterrupted first resume could have imported them as work. Without a recorded Stop, pending or unknown outcome receipts leave that run open and stop the automatic attempts for the person's decision. Permanent identity/data refusals also stop retrying; later model or importer failures do not enable this settlement path. Recorded Stop intent keeps its original meaning. Opening or reading alone does not enable these retries; a read-only Host settles nothing. Closing cancels pending timers and waits for an active attempt before releasing the data folder.

An idle checkpoint with proposed, allowed or claimed writes also reports `awaiting-decision`. The revision-bound person action can cancel that turn's unsent document writes through Core, end the old run and keep the exact recovery copies. This is an explicit choice to end the interrupted work. A dispatch that already began and an unknown outcome cannot be cancelled this way; their original receipts and data remain pending and the action reports `cleared: false` until finality is established.

`ThreadSummary.recoveryHold` is a derived signal for both conversation lists and detail views. It names the earliest blocking checkpoint and gives no permission. Ordinary running producers show no recovery hold for checkpoints they save as progress. For interrupted work the precedence is: `recovering` during an active reconciliation or repair, an in-flight dispatch, or healthy pending reconciliation; then `inspection` for damaged or unattributable data the system cannot safely import itself; then `awaiting-decision` for Core unknown outcome or checker-held effects. Damaged data wins over a separate decision; a healthy idle checkpoint stays `recovering` until reconciled. Stored effect hints never decide the signal. A Stop can finish checkpoint recovery while an unknown outcome still needs its separate receipt decision: further deliberate work is allowed, uncertainty stays visible through effects and current-work views, and move/delete refusals name the original target, turn and effect receipt for inspection in Needs you. On an idle stopped turn, `Turn.recovery` can offer a revision-bound person action, `turns.keepRecovery`, to keep the raw checkpoint and private bookkeeping as inspection copies. A stale revision, busy conversation, unsafe file or concurrent change refuses or retains the pending state. The current in-app copying capacity is 16 MiB per file; larger data remains untouched for offline inspection.

That person action closes only the conversation's own existing runs. It permissions local recovery bookkeeping only after Core confirms the task exists, every task run is closed and every task receipt is final. An unknown or held receipt keeps the checkpoint and original bookkeeping pending: `ok: true` with `cleared: false` means copies were kept, not that the conversation is unblocked. The caller must show the returned detail. Core receipts are never deleted or relabelled. Closure is journalled and its projection saved before checkpoint removal; thread events let consumers refresh the derived hold.

Private custody normally remains in the data folder until its conversation is deleted. Explicitly keeping it creates a person-requested inspection copy that can be included in a data export, always marked hidden and excluded from active restore. This is data preservation, not an encrypted portable recovery or authority-restoration contract. Implementation: [checkpoint recovery](src/composition/checkpoint-recovery.ts), [person action](src/composition/checkpoint-repair.ts) and [API](src/api.ts). The public Host/Core and real process-kill checks are in [managed paths](test/managed-paths.test.ts).

## What it replicates, from whom, when

- The engine port is shaped like the AI SDK's `HarnessV1` (`@ai-sdk/harness`, experimental; its adapters reach Pi, Codex, Claude Code, ACP and others), so an engine has an exit (`backbone-way:radar/cap-04-parallel-work.json`, evidence dated 25 Oct 2026).
- Model routes: the policy lives here and a gateway is only transport; the person's own key first, Vercel AI Gateway as the default gateway and OpenRouter as the alternative, with no silent fallback because AI Gateway can fall back to system credentials on a failed BYOK request (Vercel's docs, updated 14 Sep 2026; `backbone-way:radar/cap-10-models-accounts.json`, evidence dated 25 Oct 2026).
- A thread API of projections, commands and receipts, so another shell can host the app (`backbone-way:radar/cap-11-06-single-thread-base.json`, evidence dated 23 Oct 2026).
- Secrets at rest (all checked 26 Oct 2026): Electron's [safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage) (the Keychain-held key, the async API, why an unsigned build is asked again) and [fuses](https://www.electronjs.org/docs/latest/tutorial/fuses) (RunAsNode, NODE_OPTIONS and inspect on by default, each recommended off); [CVE-2026-70597](https://nvd.nist.gov/vuln/detail/CVE-2026-70597) (published 5 Aug 2026: Electron's same-signature parent check for those switches was a race; the workaround is the fuses) and CVE-2026-42890 (an Electron app shipped with RunAsNode on ran any code under its permission); 1Password's [CLI app integration](https://developer.1password.com/docs/cli/app-integration-security) (a CLI that holds no secret and asks the running app); Apple's TN3137 on the file-based and data-protection keychains; VS Code's move from keytar to safeStorage ([write-up](https://control-plane.io/posts/abusing-vscode-from-malicious-extensions-to-stolen-credentials-part-2/)). Lab properties S9, S18 and S22 (`work-planes-lab:docs/PROPERTIES.md`).

## Why

Surfaces and engines change faster than guarantees. With every surface on one `api`, every engine behind one engine port, and every outside action through one Gateway into the core, a surface or an engine can be replaced without touching what the core enforces, and a person sees the same receipts wherever the work came from.

## Swap it

Implement the `api` method map (`src/api.ts`) and the Gateway (`src/gateway.ts`) over the same core crossings; the app and the door depend on those types only. The stub engine (`src/stub/`) is the reference for a minimal engine.

## Remove it

Not removable while a surface uses it: the app and the MCP door stand on it. To leave, quit the app and revoke the doors (`unregisterPieceIn` ends a piece's registration, refused while one of its effects is `UNKNOWN`) (their receipts stay in the core), settle any `UNKNOWN` effects, then delete the data folder (`removeDataHome` stops its database first).
