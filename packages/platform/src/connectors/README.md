# Connector service

The person's discovered MCP servers, tool choices, permissions and held actions, behind the Core effect gateway. [The connector contract](../../../../docs/contracts/connectors.md) owns behavior; [the permission ledger contract](../../../../docs/contracts/standing-signature-ledger.md) owns permission life, checked answer basis and upgrade limits.

A permission is given in Core before its UUID is persisted locally. A automatic sending passes that UUID as structured basis; a per-call permission passes person. The Core checks the same person, workspace, live permission, exact connection and complete tool operation while holding its workspace and decision locks. It appends the answer with its basis through the normal hash chain. The definition digest is opaque: the client hashes a canonical, recursively key-sorted form of the complete SDK tool definition before redaction, and the service owns checking that digest, launches and accounts. The released blocklist sets the classification floor; only a server-annotated read meeting the narrow leading-read/final-noun exemption may count as a read. Names and sending-argument flags do not veto a person permit or a newly given permission. New permissions bind coverageVersion 1 with the original definition in the existing Core digest. Unversioned plain permissions retain the released argument restriction; unversioned blockedToo permissions retain their existing wider argument reach. A local version marker cannot upgrade the Core-bound digest. A matching legacy pin upgrades locally without changing its permission UUID or Core history; a changed legacy pin retires with definition_changed. A live changed definition retires local authority before refreshing, and duplicate names cannot identify an approved tool.

Core crossings run outside the data folder lock. A Core-first give is persisted only after a fresh locked version check, and an overtaken give gives no local authority. Decision approval is saved under the lock before answering Core outside it; dispatch checks the same permission again after every wait. Ending first removes the local permission and writes a pending end in the same durable file update. If Core is available it then ends the Core permission and clears the pending item; otherwise the local removal succeeds and the pending end waits. A late Core link or the next writable start drains it without reopening local authority. A restart retries an unconfirmed end idempotently. A crash after a committed give but before local persistence can leave an unused Core permission. Old file-only permissions are retired during reconciliation and need a new permission; they never stand in for a Core permission. A missing discovered server or moved data folder retires authority; a temporary different launch/account suspends it until the exact signed configuration returns.

The released four-argument answer function stays unchanged. Older answers without basis are distinguished from later legacy-ABI per-call answers by the additive step's ledger boundary. Owned installation follows the permission ledger contract; giving permission and tool permissions return refusal receipts until the new Core step is installed; per-call permission and discard keep using the released crossing meanwhile. External data folders require administrative installation through the exported installers, as specified in the contract.

Focused tests: packages/platform/test/connectors-signature-ledger.test.ts covers lifecycle and interrupted writes; packages/platform/test/signature-ledger-host.test.ts reconstructs a complete session from ledger rows alone; packages/platform/test/signature-ledger-upgrade.test.ts covers released histories and the unchanged legacy ABI. The existing connectors.test.ts and connectors-standing-turn.test.ts cover the call path and send races.

Listing and the other confirmation/offer reads never reconcile, query Core or create a seal key. They treat file-only permissions and missing/invalid seal keys as inactive. Writable startup or mutations retire file-only permissions and drain pending ends. Disabling a server/tool, closing a door and ending a permission do not wait for an unavailable Core; giving permission refuses plainly after a bounded Core wait.

Unknown effects pause automatic sending for the same complete tool operation on their Core connection, including across restarts and processes. Core effect rows own that pause; the existing connector file holds inspection intent and receipts, never clearance authority. Person-only inspection can confirm happened/not happened through the existing Core reconciliation ledger or keep unknown outcome closed with a local receipt. Reads, other tools, other connections and individual permissions keep their existing behavior. API-line resolution needs an explicit person capability binding and native confirmation; Host.call and ToolHost expose none. Electron main binds this capability for native card decisions and the existing asked CLI route. See the connector contract for rejected alternatives.


Consumer handoff: set() accepts an optional top-level enableStamp from enableStamp(serverId, tool?). It is checked inside change(), before any choice mutation, alongside the door/signature checks. It binds complete launch values, definitions, classifications and revisions through an ephemeral per-service HMAC key; another Host/restart needs a new question. Reading it creates no data folder file or seal key. Trusted direct calls may omit it; desktop composition requires its own native stamp and validates it through a synchronous callback inside the admitted settings write.

Tool lookups use own properties; catalogue construction keeps __proto__ as an ordinary own tool name. A standing view exposes its Core id, and held actions expose standingSignatureId from their immutable approval, including failed/unknown outcome calls and superseded permissions. signatureEndings contains only local pending/conflict IDs, never a Core acknowledgement; malformed IDs withhold that optional projection. Listings remain read-only and credential-blocked tools/statements remain withheld.

endStoredSignature(serverId, tool) acknowledges only admitted local removal and its pending Core end, even with unavailable Core or disappeared discovery. The ownership-only Host wrapper waits for ownership rather than Core, preserving closing/read-only/import guards. The app distinguishes local ending, pending Core confirmation and conflicts. Cold startup and listing still require Core.


unknown outcome evidence is retained from the positive Core dispatch ledger witness: dispatchedAt identifies admission, and dispatchReceipt contains its sequence/hash. A fresh person override cancels an unsent standing-approved effect and creates a fresh proposal with checked person basis; no dispatch bypass remains. Audit export projects that finite basis. The exact statement, immutable standingSignatureId and any fresh personReleasedAt are shown alongside it; the latter never authorizes a later send. Missing historical evidence stays absent, and listing does not repair it. Provider reads and automatic resolution are deliberately not added.

A person replacement retains its deterministic idempotency ticket with the original before Core proposes. The next effect proposal resolves outstanding tickets through Core and cancels unretained orphans; this only narrows authority and never dispatches or answers them. The replacement UUID is saved with the local receipt once Core returns it.
