# ADR 0005: Permit LGPL for unmodified, dynamically linked native libraries

**Status:** accepted 12 November 2026; implementation updated 14 November 2026. Public macOS packages require libiconv 1.18 and GNU gettext 0.26's libintl built from pinned GNU source archives, with the resulting dynamic-library digests checked against the build record. The original third-party libraries still have unknown provenance and cannot pass the public build check.

**Context.** The notices inventory identifies the native payload. The embedded PostgreSQL distribution used by the app and the CLI includes two native libraries under the GNU Lesser General Public License: **libiconv** (character-set conversion) and **libintl** (GNU gettext's message translation runtime). [ADR 0001](0001-licence-and-dependencies.md) and `scripts/licences.mjs` permit only the licences in `ALLOWED`, which does not include LGPL, so today we distribute them outside our written policy. The notices unit exposes their terms; it did not change the policy.

**Decision.** LGPL-2.1 and LGPL-3.0 are permitted only for native libraries that we ship **unmodified** and **dynamically linked**, as separate files a recipient can replace. Each such library must have:

- its licence and notice text shipped in the product (the notices screen and `backbone notices`);
- a pinned pointer to the exact corresponding source (version and archive digest) in the notices source list that the notices unit adds (scripts/notices/native.json);
- an entry naming it explicitly. There is no blanket LGPL allowance: npm packages, statically linked code and modified libraries stay outside the policy.

Today this covers exactly libiconv and libintl inside embedded PostgreSQL.

**Why.** LGPL is designed for this case: it allows distribution in a product under another licence, provided the library can be replaced and its source is available. Postgres.app and Homebrew's PostgreSQL bottles distribute the same libraries this way. Replacing them would mean maintaining our own PostgreSQL builds for every target, which costs more upkeep than the obligation it removes. Alternatives considered: build PostgreSQL without gettext and with the system iconv (removes the libraries, adds a build we maintain), or drop embedded PostgreSQL (a product regression).

**Consequences.** Run `node scripts/native-lgpl/build.mjs` once on the target Mac before a public build. It downloads only HTTPS GNU archives, checks committed SHA-256 pins and, when GnuPG is installed, verifies detached signatures against the release signer's pinned fingerprint using GNU's keyring. A matching cached build needs no network or compilation; lipo and otool still inspect its bytes. Archives, extracted source and build output stay in ignored dist/native-lgpl. The build uses a recorded minimal environment, ignoring inherited configure and make settings. Both libraries contain arm64 and x86_64 slices targeting macOS 13.0, checked with lipo and otool. GnuPG key expiry is recorded separately from signature validity. Only the two shared-library targets are used; no GNU source is patched and no static archive ships. Mach-O install names are relocated to the existing PostgreSQL paths and the files are ad-hoc signed after relocation. This is binary relocation, not a source modification.

The app uses the cached GNU build when present. An ordinary local app build without it retains the provider's libraries and reports unknown source and version in its notices. The CLI bundles native libraries and restricts the tarball to the current OS and CPU only with BACKBONE_PUBLIC_DISTRIBUTION=1; an ordinary CLI tarball always leaves native target resolution to npm, regardless of the ignored build cache. Public mode requires the rebuilt libraries in both packers. Invalid available output fails. Other platforms need their own native inventory and recipe before public distribution.

The packaged lgpl-build.json records source identities, detached signature validity and key expiry, compiler, configure flags with neutral build paths, both process environments, architectures, deployment targets, linkage and dylib digests. Public packers and public notice coverage require the current recipe digest (build script and build-support module), verified detached signature records for both pinned GNU signers, exact source pins, matching actual dylib digests, and bytes different from the committed provider-original digests. Staging also rejects replacements equal to the provider files being replaced. This checks a locally generated build record; it is not a signed build attestation or proof against a malicious builder fabricating other binaries and a record. Coverage rechecks shipped bytes even if inventory hashes are refreshed. lipo and otool bind recorded library architectures and macOS 13.0 targets to the files; staging refuses PostgreSQL binaries needing missing architectures. Other libiconv/libintl-prefixed files are refused unless they are links to one of the two rebuilt files.

Notices derive exact GNU source versions, archive URLs, digests and unmodified status from the staged record. Without that record they explicitly say source and version are unknown. The app keeps replaceable files outside app.asar at Contents/Resources/postgres/native/lib; the public CLI uses node_modules/@embedded-postgres/<platform>-<arch>/native/lib and preserves the bundle in its shrinkwrap. Release operators must preserve the exact upstream source archives for recipients. Current digests describe the ad-hoc-signed bytes; a future distribution-signing step must regenerate the record and coverage after signing.

The npm licence policy remains unchanged. Revisit if we modify or statically link either library, change target architecture, change the LGPL build recipe, or adopt a PostgreSQL distribution without these libraries. Source and focused-test evidence do not replace the packaged PostgreSQL and ready-Core checks required for a release.
